## 1. 项目定位与核心原则

### 1.1 定位



* **不捆绑任何发行版**（Arch/Ubuntu 均不依赖）：Linux 内核 + 奇点 OS 自制根文件系统。

* 需要什么组件就单独编译源码，打包成 `.qd/.qds` 模块，由模块引擎按需加载。

* 系统控制权从开机第一秒就在奇点 OS 代码手里（自研 init 是 1 号进程）。

### 1.2 核心原则



| 原则          | 说明                                                |
| ----------- | ------------------------------------------------- |
| 交叉编译        | 全部程序用 `x86_64-linux-musl-gcc` 静态编译，防止宿主库污染 rootfs |
| 不引入 systemd | 自研 init（1 号进程）承担系统主控                              |
| 不拷贝发行版 /usr | rootfs 只放自编译产物，避免大量不兼容依赖                          |
| 模块化         | 热发现 / 热插拔 / 热替换 / 调用隔离 / 统一生命周期 / 模块间总线           |
| 安全隔离        | 主系统崩溃不影响子系统；子系统侧可重启主系统                            |
| 界面真实        | 界面显示真实系统结构，不 "改样子骗用户"                             |

## 2. 总体架构（框架分层）

用户确认的架构：**主系统的框架（主框架）搭建在子系统框架下面**。



```
/
├─ boot.qds               引导文件（激活子系统）
├─ 子框架.qd/             子系统框架（顶层框架）
│   ├─ ai.qd/             AI 子系统（最小独立系统 + 专属隔离容器）
│   │   ├─ bin/ai_service    AI 服务（TCP 127.0.0.1:6800）
│   │   └─ ai.qdai           AI 约束标记文件
│   └─ 主框架.qd/           主系统的框架（搭建在子框架下）★ 唯一路径基准
│       ├─ module-engine     主系统引擎
│       ├─ 记忆.qd/          AI 统一记忆（日历索引 + 详情，见 7C）
│       └─ 资源管理.qds      统一任务管理器持久状态（资源池/分配记录，见 7C.3；管理器是 module-engine，非本文件）
├─ sbin/init              1号进程（挂载虚拟文件系统 → 引导）
├─ bin/busybox            最小用户态（静态，含 chroot/nc）
├─ modules/               模块区（.qd/.qds/.qdai 模块存放处）
└─ 仓库/                  包仓库（索引 + 实体/ 实体目录，见 7A.2）
```

### 2.1 层级语义



* **子框架.qd** = 顶层框架，承载所有子系统。

* **ai.qd** = AI 子系统：最小可运行的独立系统，配置专属 chroot 隔离容器，常驻 AI 服务。

* **主框架.qd** = 主系统的框架，**搭建在子框架下面**，即系统内路径恒为 `/子框架.qd/主框架.qd/`。里面是主系统（module-engine、记忆.qd、资源管理.qds）。**子框架与主框架连在一起**，经授权通道互通。

* **boot.qds** = 根目录引导文件：连接第一个框架（激活子系统），子系统运行后由子系统侧激活主系统。

### 2.2 后缀语义约定



| 后缀      | 含义      | 角色区分 |
| ------- | ------- | ------------------------------------------------------------------------------------------------- |
| `.qd`   | 目录单元    | 框架（子框架.qd/ 主框架.qd）/ 模块（<模块>.qd）/ 数据归档（<日期>.qd）                                                  |
| `.qds`  | 单文件     | 靠首行 `type` 字段区分：`boot`（引导脚本，如 boot.qds）/ `guide`（模块导引）/ `index`（索引）/ `resource`（资源管理）/ `memory`（记忆索引） |
| `.qdai` | AI 约束文件 | 仅 ai.qd 内一个：ai.qdai                                                                               |

> 解析规则：module-engine / ai_service 读到 `.qds` 文件先读首行 `type` 字段，再按类型解析，避免把引导脚本当元数据或反之。
>
> **例外**：`boot.qds` 不参与本解析——它由 init 直接 `exec`（首行必须是 shebang `#!/bin/sh` 才能被内核作为脚本执行），且位于根目录（不在 `/modules` 下），module-engine / ai_service 不会扫描到它；其身份按根目录路径约定（`/boot.qds`）识别，不依赖 `.qds` 首行 `type`。

## 2.2b 子系统双域权限模型

ai.qd 子系统的权限分两个域：

### 域一：框架内权限（ai.qd 容器内，天然拥有，不受限）



| 能力      | 说明                       |
| ------- | ------------------------ |
| 读       | 对框架内文件与状态的最大读取权          |
| 写       | 对框架内文件与配置的最大写入权          |
| 删       | 对框架内内容的最大删除权             |
| 服务 / 硬件 | 可调用系统服务与底层硬件（网络、内存、设备接口） |

### 域二：框架间权限（跨框架访问主系统，默认隔离）



* **默认状态**：AI 看不到主系统内容，无法读写删除，也无权调用主系统服务。

* **授权工具**（用户授予 AI，可随时撤销）：



| 工具    | 对应能力 | 授权后 AI 能做什么          |
| ----- | ---- | -------------------- |
| 眼睛（读） | 读    | 读取主系统屏幕与内容，进行可视化窗口理解 |
| 笔（写）  | 写    | 对主系统进行写入、修改          |
| 橡皮（删） | 删    | 对主系统进行删除操作           |



* **撤销行为**：任一工具被收回，AI 立即失去对应跨框架能力，回到隔离状态。

* **连通语义**：授权即连通，未授权即断开 —— 子框架与主框架相连，但通道由工具授权开关控制。

* **授权唯一来源是用户**：任何 "声明需要权限"（如 skill 声明）都只是请求，不等于授权；生效必须经用户确认（见 7A.6）。

## 3. 引导链设计（v0.3）

### 3.1 启动链路



```
Linux 内核 (bzImage 6.1.115)
  → 挂载 sos-rootfs (ext4, rw)
  → 执行 /sbin/init（奇点OS 自研 1 号进程）
  → init 挂载 proc/sys/devtmpfs
  → exec /boot.qds（引导文件，控制权移交）
     ├─ 激活 ai.qd 子系统：chroot 隔离容器 + AI 服务（监听 6800）
     ├─ 等待 AI 服务就绪（就绪判定见 3.4）
     └─ 监督循环激活主系统：while 循环 + 子进程启动 module-engine（非 exec，见 3.2）
        ├─ module-engine 接管（me> 控制台）
        └─ 主系统退出 → 自动重新激活（不影响子系统）
```

### 3.2 安全隔离机制



* **AI 服务独立进程 + chroot 文件系统隔离**：主系统（module-engine）崩溃 / 退出不影响 AI 服务运行。

* **监督循环**（boot.qds）：主系统退出后，子系统侧自动重新拉起主系统（每轮记录 "第 N 次重新激活主系统"）。实现为 **while 循环 + 子进程**（`fork+exec module-engine`，等待退出，计数后重新拉起）——**不是 exec**：exec 会用 module-engine 替换掉 boot.qds 进程，引导进程不复存在，就无法继续循环、也无法记录第 N 次。1.2"子系统侧可重启主系统"原则依赖此实现。

* **回退链**：boot.qds 缺失时，init 直接 exec `/子框架.qd/主框架.qd/module-engine`；module-engine 缺失时回退 `/bin/sh`。

### 3.3 启动参数（QEMU）



```
qemu-system-x86_64 -accel whpx -m 1024 -smp 2 \   # 骨架模式：预算 1G 为上限口径，实测占用远低于上限，1G 足够；宽裕可 -m 1536
  -kernel bzImage -hda sos-rootfs.img \
  -append 'root=/dev/sda rootfstype=ext4 rw console=ttyS0' \
  -serial file:serial.log -display vnc=127.0.0.1:1
```

> 必须带 `rw`：rootfs 只读挂载时 /tmp 无法写日志，引导文件报错。

### 3.4 就绪判定规则（v1.4 明确）



* boot.qds 轮询 `/tmp/ai.log`，匹配规则：`grep -q "就绪"`。
* **日志路径机制**：`chroot /子框架.qd/ai.qd /bin/ai_service > /tmp/ai.log` 的重定向由**外层引导进程（chroot 之外）**完成，故日志落在主环境根 `/tmp/ai.log`，不是容器内路径（容器内 `/tmp` 映射为 `/子框架.qd/ai.qd/tmp`，未被写入）。这就是验证记录中 PID=79 能就绪的原因。
* **串口"就绪"行与 /tmp/ai.log 的关系**（v1.7 明确，消除 3.4 与 6 节的表面矛盾）：ai_service 的"就绪"行**同时输出到 stderr（未重定向，串口可见）**，其余日志走 stdout 进入 `/tmp/ai.log`；boot.qds 用 `grep -q "就绪"` 匹配的是 `/tmp/ai.log`（stdout 侧）。因此串口 serial.log 可见 `奇点OS AI 服务 v0.1 就绪`（serial.log 原始行号，见 6 节）与 /tmp/ai.log 可被 grep 到"就绪"**不矛盾**——两条输出通道并存，实现上由 ai_service 在启动成功时 `fprintf(stderr, "就绪")` + `printf("就绪")` 双写保证。
* 当前 ai_service 仅在启动成功时打印一次 "就绪"，无中间态误判风险；若后续引入启动中间态，判定规则改为整行匹配 `^奇点OS AI 服务.*就绪`。

## 4. 组件说明

### 4.1 init.c —— 1 号进程



* 源码：`init/init.c`，交叉编译静态产物 → `/sbin/init`。

* 职责：挂载 proc /sysfs/devtmpfs → 打印启动横幅 → `exec /boot.qds`。

* 回退链：boot.qds 缺失 → 直接启动 `/子框架.qd/主框架.qd/module-engine`。

* 避坑：头文件用 `<sys/mount.h>`；/dev 必须挂 devtmpfs（tmpfs 会覆盖 mknod 节点）。

### 4.2 boot.qds —— 引导文件（v0.3）



* 源码：`引导/boot.qds`（shell 脚本，busybox ash 可执行）。

* 职责：

1. 挂载 ai.qd 容器的 devtmpfs；

2. `chroot /子框架.qd/ai.qd /bin/ai_service` 启动 AI 服务（日志机制见 3.4）；

3. 轮询 `/tmp/ai.log` 确认 "就绪"（规则见 3.4）；

4. 监督循环激活主系统（崩溃自动重启）。

### 4.3 module-engine.c —— 主系统引擎



* 源码：`模块引擎/module-engine.c`，静态编译 49K。

* 位置：`/子框架.qd/主框架.qd/module-engine`。

* 职责：扫描 `/modules` 下 `.qd/.qds/.qdai` 模块项；交互命令 `help/list/info/shell/reboot/poweroff`；`me>` 控制台接管系统。

* 规划扩展：install/remove/repo（7A.4）、config get/set（7A.4）、MEM 内存申请（7C.3）、MEMO 记忆指令（7C.4）、6801 内部链路（7C.5）—— 均挂在本引擎下。

### 4.4 ai_service.c + ai.qdai —— AI 子系统



* 源码：`ai.qd/ai_service.c`，静态编译；位置 `/子框架.qd/ai.qd/bin/ai_service`。

* 服务：TCP 127.0.0.1:6800，指令 STATUS / HELLO / ECHO / HELP；状态如实报告（"引擎：待接入本地 LLM"）。

* 约束文件 `ai.qdai`（**v0.3 起八段式**：身份 / 资源 / 权限模型 / 框架连通 / 职责 / 约束 / 架构 / 升级路径；早期 v0.1 为三段式）：


  * 框架内：AI 拥有读写删最高权限 + 系统服务 / 底层硬件调用权（仅限容器内）；

  * 框架间：默认隔离，跨框架访问主系统必须经工具授权（眼睛 = 读 / 笔 = 写 / 橡皮 = 删），可随时撤销；

  * 资源：骨架 ≤1G、本地 AI ≥3.5G、记忆挂主系统、内存可向主系统申请（永久 / 借用）；

  * 架构：子框架与主框架相连，子系统激活主系统、主系统崩溃由子系统侧重启。

**验证结论**：内核 → init → boot.qds → ai.qd 子系统（chroot + AI 服务）→ 子系统激活主系统（module-engine）全链通过。

> **时序说明**：日志中 `[引导] ... 已就绪 (PID=79)` 出现在 AI 服务打印"就绪"之前，属 stdout 缓冲 / 后台重定向造成的行序差异，不代表真实时序——实际是 boot.qds 轮询到"就绪"字样后才打印该行（见 3.4）。串口可见的 `奇点OS AI 服务 v0.1 就绪`（serial.log 原始行号）来自 ai_service 的 stderr（未重定向），与 /tmp/ai.log 内的 stdout"就绪"并存，机制见 3.4。

## 7A. 包管理与 Skills 仓库设计（极简版）

### 7A.1 设计决策

**要包管理，但不用重量级包管理器**（不引入 APK/DEB/ 依赖解析器 ——4GB 内存极端环境扛不住）。

包管理 = 现有模块引擎的内置子命令 + ai.qd 内的 skills 仓库。

**安装本质上 = 往 /modules 放 .qd**（热发现由引擎扫描承担），包管理只做受控的 "放进去 / 拿出去" 入口。

### 7A.2 目录结构



```
/modules/                         主系统模块区（module-engine 管理）
└─ <模块>.qd/
    └─ .qds                       type=guide（身份/功能/入口/版本/校验）
/子框架.qd/ai.qd/skills/         AI skills 仓库区（ai_service 管理）
└─ <skill>.qd/
    └─ skill.qds                 type=guide（能力定义 + 所需权限声明）
/仓库/
├─ <仓库>.qds                    type=index（模块名/来源/版本/校验和）
└─ 实体/                         模块实体存放处（本地仓库的模块本体）
    └─ <模块>.qd/                install 的拉取源（当前阶段）
```

### 7A.3 统一概念



| 概念       | 落地                   | 说明                              |
| -------- | -------------------- | ------------------------------- |
| 包 / 插件   | `.qd` 模块目录           | 系统组件单元                          |
| 包元数据     | 目录内 `.qds`           | `type=guide`，同时承担 "导引 + 包描述"    |
| Skills 包 | ai.qd 内 `<skill>.qd` | AI 能力定义，可**声明**所需工具权限           |
| 仓库       | `.qds` 索引 + 实体目录     | 索引列出模块；实体目录存模块本体                |
| 拉取源      | 当前：`/仓库/实体/`         | 网络未就绪前的本地拉取源；网络阶段开放 URL（见 7A.5） |

### 7A.4 命令接口

主系统（module-engine，`me>`）：



```
install <模块> [--repo <仓库>]    # 从仓库实体目录复制到 /modules
remove <模块>                     # 卸载（移出 /modules）
list                              # 已装模块列表
info <模块>                       # 详情（读 .qds type=guide）
repo add <仓库.qds>               # 添加仓库（登记索引）
repo list                         # 仓库列表
config get <模块>                  # 查看模块配置（如 ai.qd 的 memory_max 当前值）
config set <模块> <键> <值>         # 修改模块配置（如 config set ai.qd memory_max 4096M）
```

> `config set` 是模块界面对配置的修改入口（memory_max 修改的唯一合法途径，见 7B.3）：**config set 由用户直接操作即生效**（审批人 = 用户本人，变更写入审计段），不需要再走一次"用户确认"；7C.3 的"用户确认"只针对 **AI 发起的 `MEM REQUEST permanent`**——那是 AI 请求、用户审批；而 config set 是用户自己动手改配置，本质是用户对自己行为的授权。

AI 子系统（ai_service，TCP 6800）：



```
SKILLS LIST                        # 已装 skills
SKILLS INSTALL <skill>             # 从 skills 仓库安装
SKILLS REMOVE <skill>              # 卸载
```

skill.qds 示例字段：名称 / 触发方式 / 调用说明 / 所需权限声明（眼睛 / 笔 / 橡皮）。

### 7A.5 仓库来源与网络约束（v1.4 补齐）



* **当前阶段（网络未开始）**：仓库实体 = 本地目录 `/仓库/实体/<模块>.qd`，install 从该目录复制。无网络依赖。

* **网络阶段（路线图阶段 10）**：仓库索引增加 `source: url` 字段，install 从 URL 拉取；在网络未落地前，任何 `source: url` 条目标记为 "不可用" 并在 install 时报错，不得静默失败。

### 7A.6 权限安全闭环（v1.4 补齐）



* **skill 声明 ≠ 授权**：skill.qds 里的 "所需权限" 只是**请求**，不是生效授权。

* 安装流程：`SKILLS INSTALL` 或 `install` 时，若 skill 声明了工具权限，主系统提示用户确认授权（或拒绝仅以骨架模式安装）；

* 运行时：AI 执行该 skill 时仍受双域权限开关约束 —— 用户未授出的眼睛 / 笔 / 橡皮，AI 无对应跨框架能力。

### 7A.7 权衡说明



* 轻量：不新增独立包管理器二进制，命令并入现有引擎；

* 格式统一：.qds 同时是导引与元数据（type=guide），无额外格式；

* 版本 / 校验：.qds 声明 version + 校验和（第一版不做签名，保持轻量）；

* 热插拔：安装后引擎扫描即发现；移除即消失（与现有 /modules 扫描逻辑一致）。

## 7B. 性能与内存预算

### 7B.1 硬约束（用户确认）

目标环境：**无 GPU、极端环境（最低 4GB 整机内存）**。



| 场景             | 应用层预算                        | 整机口径说明                                                  |
| -------------- | ---------------------------- | ------------------------------------------------------- |
| 不启动本地 AI（骨架模式） | ≤ 1G（主 0.5G + ai.qd 骨架 0.5G） | 1G 为**应用层**预算；整机 ≥1G（`-m 1024` 已实测可跑）；≥1.5G 为规划余量（内核 ~50–100MB、devtmpfs、日志另计），宽裕可 `-m 1536` |
| 启动本地 AI        | 4G 整机可跑（主 0.5G + AI 基础 3.5G） | 3.5G 为模型 + 推理运行时预算；QEMU 验证用 `-m 4096`                   |

> 口径说明：QEMU `-m 1024` 对应骨架模式验证。**口径对齐**：预算 1G 是应用层上限（主 0.5G + ai.qd 骨架 0.5G），骨架实测占用远低于此上限（最小 demo 已验证 -m 1024 可跑通），内核/日志开销包含在 1024MB 内仍有余量，故 1G 足够；如需更宽裕可 `-m 1536`。`-m 4096` 对应带 AI 验证。两种目标不冲突：骨架模式面向 "无 AI 也跑得动" 的轻场景，4G 是启动本地 AI 的门槛。**"≥1.5G 为规划余量"是针对完整 AI 场景与后续功能增长的保守规划值**，与骨架实测不冲突（保守规划 vs 实测）。

### 7B.2 ai.qd 资源要求



1. **核心功能**：在最小可用系统内为 AI 提供运行环境，并封装为可调用的 API（TCP 6800 统一出口）。

2. **基础占用**：用户启动 ai.qd 本地 AI 服务时，基础内存**至少 3.5G**（模型 + 推理运行时）。

3. **主系统占用**：主系统必须在 **0.5G** 内存下正常运行。

4. **动态设置**：用户可在模块界面为 ai.qd 设置更多可调用内存（memory\_max）。

### 7B.3 资源配置字段（ai.qd 配置 .qds）



```
[资源]
engine: 骨架              # 可选: 骨架(不加载模型) / 本地LLM
memory_min: 3584M         # 启动本地 AI 的基础内存（单位 MB 或 M）
memory_max: 4096M         # 可调上限，用户在模块界面修改（永久提升的唯一合法途径）
swap_policy: off          # 可选: off / on
```



* **memory\_max 是用户侧配额**：用户在模块界面修改并持久化。

* AI 侧 `MEM REQUEST permanent` 不等价于自行改 memory\_max—— 永久提升必须经用户确认（见 7C.3 安全约束）。

### 7B.4 预算落实原则



* 主系统 0.5G 预算：module-engine 等全部静态 musl 编译、无重型依赖、无常驻多余进程；

* ai.qd 骨架 0.5G：仅 TCP 监听 + 状态接口，不预加载模型、不存记忆；

* 模型加载只发生在用户显式启动本地 AI 后（按需调用、用完可卸载）；

* QEMU 验证：`-m 1024`（骨架模式）/ `-m 4096`（带 AI）分别测。

## 7C. 记忆挂主系统 + 统一任务管理器

### 7C.1 设计决策



* **记忆不放 ai.qd 容器内**：AI 记忆挂载到主系统（主框架），ai.qd 层只留 "计算" 不留 "存储"，减少 ai.qd 的存储与运行内存。

* **统一任务管理器**：ai.qd 子系统与主系统通用同一个任务管理器（主系统侧）。

* **记忆访问申请制**：AI 读写记忆必须向主系统申请（与工具授权模型衔接）。

### 7C.2 目录结构（路径基准：/子框架.qd/主框架.qd/）



```
/子框架.qd/主框架.qd/                主系统
├─ module-engine                     主系统引擎
├─ 记忆.qd/                          AI 统一记忆（挂主系统）
│   ├─ 索引.qds                      type=memory（日历索引：日期 → 简介一行）
│   └─ <日期>.qd/                    详情文件（按日归档）
└─ 资源管理.qds                      type=resource（任务管理器持久状态：资源池/分配记录/审计日志）
```

### 7C.3 统一任务管理器（行为定义，v1.4 补齐）

**管理器 = 主系统侧程序（挂 module-engine）**，`资源管理.qds` 只是它的持久状态文件，不是管理器本身。

任务模型：



* **任务注册**：AI（或主系统内组件）登记任务：`TASK REGISTER <任务名> <所需内存>`，返回 `task_id`。

* **任务跟踪**：任务持有期间，管理器按心跳（`TASK HEARTBEAT <task_id>`，默认每 30s）确认存活。

* **任务完成**：`TASK DONE <task_id>` → 管理器回收该任务的借用内存。

* **超时兜底**：心跳缺失超 3 个周期（90s）→ 判定任务失联，强制回收借用内存。

内存申请协议（ai_service → 主系统：经 **6801 内部链路**转发，见 7C.5；6800 是 AI 入站端口，不承载转发）：



| 指令                                  | 说明                         |
| ----------------------------------- | -------------------------- |
| `MEM REQUEST <大小> permanent`        | 申请**永久**分配（须用户确认，见下）       |
| `MEM REQUEST <大小> borrow <task_id>` | 申请**借用**（绑定任务，完成 / 超时自动释放） |
| `MEM RELEASE <req_id>`              | 释放指定借用                     |
| `MEM STATUS`                        | 当前分配 / 剩余资源池               |



* **永久分配（安全约束）**：AI 发起 permanent 申请后，管理器**不得自行批准**—— 转交用户确认（模块界面 = module-engine me> 控制台，见 7C.5）；**用户拒绝则直接拒绝（不自动降级为 borrow）**：borrow 必须绑定 task_id，permanent 无任务上下文，降级语义不闭合；如 AI 需要临时额度，另行发起带 task 的 `MEM REQUEST borrow`。所有 permanent 变更写入 `资源管理.qds` 审计段（谁 / 何时 / 额度 / 审批人）。**落地方式（v1.9 明确）**：用户确认后，由用户在 me> 控制台亲自执行 `config set ai.qd memory_max <值>` 落地（与 7A.4"config set 用户直操作即生效"一致，审计段审批人 = 用户本人）；module-engine 不代用户修改配置，仅负责把确认结果回执给 ai_service。这样"memory_max 唯一合法途径 = 用户 config set"（7B.3）与"AI 经用户确认可永久提升"（7C.3）两条语义闭合。

* **借用（有限时间）**：等价借内存跑临时任务，`TASK DONE` 或超时后自动归还资源池。

* 典型场景：ai.qd 识别到运行内存不够 → `MEM REQUEST ... borrow <task_id>` → 任务完成 → `TASK DONE` → 自动释放。

### 7C.4 记忆申请协议（v1.4 补齐指令与通道）

通道与发起主体（v1.7 统一）：
- **ai_service 内部自身发起**（如启动期资源探测、AI 运行中自我申请）：直接经 **6801** 转发主系统，不经 6800（不需要"经 6800 进自己"）。
- **外部调用方代 AI 发起**（用户 / 其他模块经 AI 入口申请）：经 **TCP 6800 → ai_service** 校验 → 再经 **6801** 转主系统 module-engine（MEMO 指令）处理（见 7C.5）。
- 授权按 2.2b 工具模型（记忆读写属 "眼睛 / 笔" 域，需用户已授对应工具或记忆专项授权）。



| 指令                     | 说明                            |
| ---------------------- | ----------------------------- |
| `MEMO INDEX`           | 读 索引.qds 全部简介行（日历索引，几百字节，防短路） |
| `MEMO READ <日期>`       | 申请读某日详情文件（需授权）                |
| `MEMO WRITE <日期> <内容>` | 申请写入某日归档（需授权；仅写入申请条目）         |
| `MEMO SEARCH <关键词>`    | 在索引简介中检索（命中后再 READ 详情）        |



* 防短路：AI 默认只读 `MEMO INDEX` 简介列表，命中才申请 `MEMO READ` 详情；禁止一次拉取全部详情进上下文。

* 好处：ai.qd 容器无大存储，骨架 0.5G 预算更稳；记忆统一归档，第三方 AI 记忆也经此中转。

### 7C.5 主系统侧链路与模块界面（v1.5 补齐）

**主系统侧链路（ai_service → module-engine）**：
- 端口分工：`6800` = AI 入口（外部 / 用户调用 AI 的入站端口）；`6801` = AI ↔ 主系统内部链路（ai_service 作为客户端连接 `127.0.0.1:6801` 转发 TASK / MEM / MEMO）。
- 实现：module-engine 启动时绑定 6801 入站监听，主循环用 poll 同时服务 `me>` stdin 与 6801 socket；**不依赖模块总线**（总线仍 ⬜ 未开始，本链路独立成立，阶段 5 可据此接线）。
- 数据流：外部指令 → 6800（ai_service）→ 6801（module-engine 处理）→ 经 6801 回 ai_service → 6800 回调用方。

**模块界面（用户操作/决策入口，v1 = module-engine 控制台）**：
- 形态：module-engine 的 `me>` 交互控制台（当前经 QEMU 串口 ttyS0 / VNC 终端操作）。它是永久内存审批（7C.3）、memory_max 修改（7B.3）、skill 授权确认（7A.6）等**用户操作/决策的唯一载体**——统一用"操作/决策入口"表述，不再以"用户确认"一把罩：其中 `config set`（memory_max 修改）由用户**直接操作即生效**，不属于"AI 请求待确认"（见 7A.4）；"用户确认"仅指 AI 发起、需用户审批的请求（如 7C.3 永久分配、7A.6 skill 授权）。
- 流程示例（SKILLS INSTALL 确认）：ai_service 收 `SKILLS INSTALL` → 转发 6801 → module-engine 在 `me>` 打印"待确认：为 skill 授出 眼睛/笔？[y/n]" → 用户在控制台输入 → 结果回执 ai_service → 6800 回调用方。
- v2（路线图阶段 11）：图形界面作为控制台的前端，交互逻辑不变。
