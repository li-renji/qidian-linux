## 1. 模块定义（总则）

### 1.1 模块是什么

**模块** = 基于包管理机制，把**系统级功能**封装为**支持热替换**的单元。

- **系统级功能全部模块化**（奇点OS体系本身的一部分，要被系统调用/替换/约束）：模块引擎、包管理、渲染器、用户态、AI 服务、桌面环境（图形会话，可换）；
- **软件级不模块化**（给用户用的第三方应用，直接底层 Linux 包管理安装）：浏览器、编辑器、办公软件、播放器、文件管理器等；
- 判断标准一句话：**它是不是奇点OS系统骨架的一部分？是 → `.QD` 模块；不是 → 底层包管理直接装**（见 §2.5）；
- 模块是系统组成的最小可替换单位；
- 模块与模块之间**只有调用关系，没有更多关系**：独立打包、独立生命周期、独立安全边界。

### 1.2 模块特性（用户确认）

| 特性 | 含义 |
| --- | --- |
| 响应迅速 | 模块加载即用，不引入重量级依赖；静态 musl 编译，无动态库解析开销 |
| 结构简单 | 一个模块 = 一个 `.QD` 文件夹，内部结构固定（本体 + 调用逻辑 + 契约） |
| 高度可自定义 | 不满意的模块可整体取下，替换为自写或第三方模块；系统其余部分不受影响 |

### 1.3 模块化六要素（硬性要求）

| 要素 | 落地 |
| --- | --- |
| 热发现 | 系统启动 / 运行中扫描 `/modules` 下全部 `.QD` 文件夹 |
| 热插拔 | 放入即被扫描发现、移除即消失，无需重启 |
| 热替换 | 旧模块从 `/modules` 移出（或停用），新模块放入，加载逻辑切到新模块 |
| 调用隔离 | 模块间的调用只经约定入口（`.QDS` 的 `entry` / 调用段），互不侵入 |
| 统一生命周期 | 加载 / 运行 / 卸载由 module-engine 统一管理（模块总线） |
| 模块间总线 | module-engine 承担总线：命令转发、状态查询、事件通知 |

## 2. 包管理机制（核心）

### 2.1 打包形式：`.QD` 文件夹

**将程序本体与调用逻辑打包为一个 `.QD` 文件夹**：

```
<模块>.qd/                  # .QD 文件夹 = 一个包（模块）
├─ bin/                     # 程序本体（静态 musl 二进制，交叉编译）或启动入口脚本
│   └─ <entry程序>           # 模块可执行入口
├─ data/                    # 模块私有数据（可选：主题、图标、配置模板）
├─ 配置                     # 模块配置（可选，默认空）
└─ .qds                     # 调用逻辑与契约（导引文件）
```

> **两阶段安装（重量级组件，当前无在册实例）**：程序本体可以是"系统区依赖"而非全部塞进 bin/——系统库（gtk3 等）经系统包管理（Alpine apk 或源码编译）装进系统区，模块本体承载启动逻辑 + 配置 + 契约（`.qds` 以 `sys_deps` 声明系统区依赖）。**v1.4 更正：原实例桌面.qd（Xfce）未落地且已废弃；sys_deps 当前未解析**。见 §2.4。

### 2.2 加载流程：启动扫描全部 `.QD`

系统启动时（module-engine 启动即执行）：

```
内核 → init → boot.qds → module-engine
  → 扫描 /modules 下全部 .QD 文件夹（热发现）
  → 逐个读取 .QD 内的 .QDS 文件（type=guide）
  → 按 .QDS 声明注册模块（身份 / 入口 / 调用边界 / 安全边界）
  → 模块进入"已发现"状态（可被 list 查看、可被调用）
  → 用户/系统按需 run 模块（启动入口程序）
```

- 扫描覆盖：`/modules/` 下全部 `.qd` 目录；AI 侧另有 `/子框架.qd/ai.qd/skills/` 的 skills 扫描（由 ai_service 管理）；
- 运行时热发现：module-engine 周期性检查 `/modules` 目录变更（mtime 检测），新放入的 `.QD` 自动注册，移除的自动注销；
- **注册范围（v1.4 按源码核账）**：注册表仅含模块名 / entry / version / desc（read_contract 解析范围）；sys_deps、security、ai_call、sys_call 不在注册与校验范围。

### 2.3 `.QDS` 文件：定义调用与安全边界

`.QDS` 是模块的**导引 + 元数据 + 调用契约**，用于定义 QD 的：

1. **AI 调用**：AI 如何调用本模块（入口、参数、返回）；
2. **系统调用**：主系统/其他模块如何调用本模块（入口程序、命令格式）；
3. **安全边界**：模块能做什么、不能做什么（权限声明、隔离范围、风险级别）。

### 2.4 两阶段安装流程（重量级组件，v1.1 提出；当前无在册实例）

轻量自研组件：**单阶段**——musl 静态交叉编译 → 打包 `.QD` → 放入 `/modules`（零系统依赖）。

重量级组件（依赖 GTK3/glib/X11 生态，musl 静态编译不可行）理论上走**两阶段**：

```
阶段①  系统库进系统区
        经系统包管理（Alpine apk）安装到 /usr（Xorg / gtk3 / dbus / xfce4-session 等）；
        或源码编译后放入系统区——来源在 .qds 的 sys_deps 中如实声明。
阶段②  程序本体 + 调用逻辑封装 .QD
        bin/     启动入口脚本（模块如何拉起图形会话）
        data/    配置 / 主题 / 面板模板
        .qds     契约：entry + sys_deps（声明阶段①的系统区依赖）
        → 放入 /modules，由 module-engine 统一注册、统一生命周期
```

- **现状更正（v1.4）**：v1.1/v1.2/v1.3 声称的实例"桌面.qd（Xfce 两阶段安装）"**实际未实现且 Xfce 路线已废弃**（boot.qds v0.10 改为自研桌面：渲染器 fbdesktop + 用户态 uis，musl 静态单阶段，零系统区依赖）。两阶段安装保留为**通用机制设计**，当前无在册组件；
- **sys_deps 校验（规划）**：module-engine 当前**未解析 sys_deps 字段**（契约解析仅 entry/version/desc，见 §3.2 与开发文档 v1.13 §7）；"启动模块前检查系统区依赖是否存在"的校验逻辑随模块总线（阶段 9）落地；
- **因果一致性**：删除某组件模块时，仅服务于它的配置 / 开关 / 调用一并清理（§4.3 纪律同样适用）。

### 2.5 模块化边界：系统级 vs 软件级（v1.2）

**系统级功能全部需要模块化；软件级不需要模块化。** 两条包管理各司其职，不重复、不冲突：

| 层级 | 包管理 | 管辖对象 | 示例 |
| --- | --- | --- | --- |
| 系统级 | 模块包管理（`包管理.qd` + module-engine） | 奇点OS 系统骨架、可热替换的系统能力 | 模块引擎、包管理、渲染器、用户态、AI 服务、桌面环境（图形会话；**桌面.qd 待建**） |
| 软件级 | 底层 Linux 包管理（Alpine apk / pacman / apt） | 用户安装的第三方应用与系统库 | 浏览器、编辑器、办公软件、Thunar 文件管理器、gtk3 等库 |

**判断标准（一句话）**：它是不是奇点OS系统骨架的一部分？**是 → `.QD` 模块；不是 → 底层包管理直接装。**

- 图形会话保留模块化目标（**桌面.qd 待建**）：当前实际图形会话 = 自研桌面（`用户态.qd/bin/uis` 前台 + `渲染器.qd/bin/render` fbdesktop），**尚不是独立 .QD 模块**——它是 boot.qds v0.10 的 start_uis 段直接 exec 的（见开发文档 v1.13 §4.2.1）；封装为 `桌面.qd` 属待建工作，完成后换桌面 = 移出旧模块、放入新模块，无需改引导；
- 换底层发行版：系统库重新用该发行版的包管理装，`/modules` 的 `.QD` 模块原样保留（sys_deps 校验随模块总线落地后跟着改）；
- 模块的 `sys_deps` 契约正是两层衔接点：模块声明它需要哪些系统区依赖，module-engine 装前校验。

### 2.6 可选拉取模块：软件级的一种分发形态（v1.3 新增，REA/QD 浏览器类别裁决）

§2.5 的判断标准（"系统骨架的一部分？是 → .QD；不是 → 底层包管理直接装"）在**可选工具软件**上遇到一个中间形态：像 REA（逆向工具箱，Node 22+）这类第三方工具，本质是**软件级**（不是奇点OS 骨架），但用户希望走 `install <名>` 这条熟悉的包管理通道"按需快捷拉取"，而不是去 apk 里手动找。裁决如下：

| 类别 | 归属 | 分发通道 | 是否进镜像 | 实例 |
| --- | --- | --- | --- | --- |
| 系统级骨架 | `.QD` 模块 | `/modules` + module-engine | 进默认镜像 | 模块引擎、包管理、渲染器、用户态、AI 服务、桌面.qd（待建） |
| 普通软件级 | 底层 Linux 包管理（apk） | 系统包管理直接装 | 按需 | 浏览器（QD 浏览器品牌保留）、编辑器、办公软件、Thunar、gtk3 库 |
| **可选拉取模块（v1.3 新增）** | **软件级**（不具系统骨架地位），但**走 `.QD/install` 仓库通道做"按需拉取"的入口** | `/仓库/实体/<名>.qd` 预置 + `install <名>` 复制到 /modules；网络自动拉取待 `source: url` 就绪 | **不进默认镜像、不占启动内存** | REA |

- **REA 裁决**：REA 是第三方工具软件，按 §2.5 属**软件级**；但它与奇点OS AI 体系契合（本地 Agent + 工具按需加载），采用"可选拉取模块"形态——仓库预置 `/仓库/实体/REA.qd/`，`install REA` 即从本地仓库复制到 /modules（现有 pm.c install 流程可用），未启用零占用；重依赖（Ghidra 12.1.4 + 64-bit JDK 21，或 Hopper；Node 22+）由用户自备，REA 不下载不改动它们；`remove REA` 时同步清除 skills 注册、6801/6802 配置引用、仓库索引条目（§4.3 因果一致性）。
- **QD 浏览器裁决**：浏览器属软件级，**不做成 .QD 模块**；落地为软件级应用，品牌保留"QD 浏览器"。内核选型：默认候选 2（links/lynx 类轻量文本浏览器，符合轻量定位）；WebKitGTK 为普通硬件可选（几百 MB 内存设备默认不装）。
- **与 §2.5 原则不冲突**：可选拉取模块只是"软件级软件走了 .QD 的仓库/安装入口"，它在系统地位上仍是软件级——不承担系统骨架职责、可整体移除而不破坏系统；这是分发形态的补充，不是把软件级重新定义成系统级。

## 3. `.QDS` 契约格式（type=guide）

### 3.1 当前已实现字段

```
type=guide
name=<模块名>
version=<版本号>
desc=<功能描述>
entry=<入口程序相对路径>
sys_deps=<系统区依赖列表，逗号分隔>   # 规划位：当前 module-engine 未解析此字段；两阶段安装无在册实例
```

实例如下（`/modules` 现存模块，v1.4 按实际核账）：

```
# 包管理.qd/.qds
type=guide
name=包管理
version=1.0
desc=主系统包管理模块：install/remove/repo/list/info，从 /仓库/实体 安装到 /modules
entry=bin/pm

# 渲染器.qd/.qds
type=guide
name=渲染器
version=2.0
desc=主系统渲染器模块：文本组件 + fb自绘图形后端（fbdesktop/fbfile/fbbar），完整中文显示，可替换
entry=bin/render

# 用户态.qd/.qds
type=guide
name=用户态
version=2.0
desc=主系统用户态模块：VNC 图形会话（fb自绘+raw键盘，中文完整显示；无fb回退文本）
entry=bin/uis
```

仓库实体（`/仓库/实体/`，可选拉取模块，v1.3 预置）：

```
# REA.qd/.qds
type=guide
name=REA逆向工具箱
version=1.0
entry=bin/rea.sh
desc=可选逆向工具（Node 22+，npx rea-agents）；Ghidra 12.1.4 + JDK21 / Hopper 用户自备，本模块不下载不改动
permissions=file,exec,net

# QD浏览器.qd/.qds
type=guide
name=QD浏览器
version=1.0
entry=bin/qd-browser.sh
desc=轻量文本浏览器（links/lynx/elinks 任一即启动）；软件级应用，低内存设备不预装
permissions=net
```

> **v1.4 更正**：v1.2/v1.3 列出的"桌面.qd/.qds（两阶段安装实例）"**实际不存在**（/modules 无此模块，Xfce 已废弃）——已从实例清单移除，两阶段安装降为通用机制设计（§2.4）。

### 3.2 统一契约字段（规范，含规划位）

| 字段 | 必需 | 含义 |
| --- | --- | --- |
| `type` | ✅ | 契约类型，必须 `guide`（导引）；首行读取用于类型分派 |
| `name` | ✅ | 模块名（唯一标识） |
| `version` | ✅ | 模块版本 |
| `desc` | ✅ | 功能描述（供 list/info 展示） |
| `entry` | ✅ | 入口程序相对路径（bin/xxx） |
| `sys_deps` | 规划 | 系统区依赖列表（逗号分隔）；字段已定义，**module-engine 当前未解析**（v1.4 更正：原 v1.2 标"条件/已实现"有误） |
| `ai_call` | 规划 | AI 调用定义：AI 侧如何调用本模块（触发词 / 参数 / 返回格式） |
| `sys_call` | 规划 | 系统调用定义：主系统或其他模块的调用接口（命令 / 参数 / 返回） |
| `security` | 规划 | 安全边界：权限声明（所需工具：眼睛/笔/橡皮）、风险级别、隔离要求 |
| `check` | 规划 | 校验和（安装时校验，防篡改；第一版不做签名，保持轻量） |

> 现状说明（v1.4 按源码核账）：**已解析**：`entry / version / desc`（及目录名即 name）——module-engine `read_contract` 实际读取范围；`type` 仅用于"缺契约报错"提示（首行非 `type=guide` 时报自检失败）。**未解析**：`sys_deps`（无任何读取代码）；`permissions` 字段由 ai_service 侧读取（REA/QD浏览器 .qds 已用）。`ai_call / sys_call / security / check` 为统一契约的规范定义，随模块总线（阶段 9）逐步落地。任何模块未声明 `security` 前，默认按"无跨框架权限"处理（安全边界默认收紧）。

### 3.3 `.QDS` 解析规则

- module-engine / ai_service 读到 `.QDS` 文件**先读首行 `type` 字段**，再按类型解析（`guide` = 模块导引；`index` = 仓库索引；`resource` = 资源管理；`memory` = 记忆索引）；
- **例外**：`/boot.qds` 不参与本解析——由 init 直接 `exec`（首行必须是 shebang `#!/bin/sh`），身份按根目录路径约定识别；
- 缺少 `.QDS` 的 `.QD` 目录：视为无效模块项，扫描时报告"契约缺失"（如 坏模块.qd 的自检失败提示），不加载入口。

## 4. 模块热替换

### 4.1 替换流程（用户确认的语义）

替换 = **旧模块存为存储（停用/移出），内存不再读取旧模块，系统开始读取新模块**：

```
1. 准备新模块（自写或第三方）：新模块.qd/（含 bin + .qds）
2. 停用旧模块：把旧模块.qd 从 /modules 移出（移到 /仓库/实体/ 或备份区，保留但不加载）
3. 放入新模块：把新模块.qd 复制进 /modules
4. 热发现：module-engine 扫描到新 .QD → 注册新模块 → 后续调用走新模块
5. 校验：list 确认新模块已注册、info 确认契约正确；旧模块不再出现在列表
```

### 4.2 热插拔细节

- **放入即发现**：复制进 `/modules` 后，下一次扫描周期（或手动 `list` 触发重扫）即注册；
- **移除即消失**：移出 `/modules` 后，模块从注册表注销，相关调用立即失败（明确报"模块未安装"）；
- **替换不影响运行中的其他模块**：模块间只有调用关系，替换 A 模块不影响 B 模块的运行；
- **卸载顺序**：先停用（移出）再清理数据，避免运行中引用残留。

### 4.3 替换的因果一致性（用户纪律）

删除 / 替换必须按**因果树连根删**：

- 若模块 A 被替换，则所有"因 A 而创建"的关联物（A 的配置、A 产生的数据归档、仅服务于 A 的调用开关）必须随 A 一起停用或清理，不得残留孤立开关 / 孤立调用；
- 例：删除某动效模块时，动效开关、动效相关按钮必须一并删除——不允许"功能删了开关还在"。

## 5. 命令接口

### 5.1 主系统侧（module-engine，`me>`）

```
list                              # 已装模块列表（含版本 / 状态）
info <模块>                       # 详情（读 .qds type=guide 全字段）
install <模块> [--repo <仓库>]     # 从仓库实体目录复制到 /modules（热插拔）
install <模块> --url <https://…>   # 网络来源安装（v1.3 规划：远程仓库 source: url 就绪后开放）
remove <模块>                     # 卸载（移出 /modules）
repo add <仓库.qds>               # 添加仓库（登记索引）
repo list                         # 仓库列表
config get <模块>                  # 查看模块配置（如 ai.qd 的 memory_max）
config set <模块> <键> <值>         # 修改模块配置（用户直接操作即生效，写入审计）
```

**`install --repo` 参数解析修复说明（v1.3 记录的缺陷）**：当前 pm.c 在解析 `install <模块> [--repo <仓库>]` 时**未真正解析 `--repo` 这个可选参数**（缺陷）——无论是否带 `--repo`，都只从默认本地 `/仓库/实体/` 复制，指定仓库被静默忽略。修复方向：parse 参数时识别 `--repo <仓库名>`，据此选择对应仓库索引目录；未指定时回退默认仓库。**网络来源命令 `--url`**：在远程仓库 `source: url` 就绪（路线图阶段 10）前，`install --url <...>` 明确报"网络仓库未就绪"，不得静默走本地或假装联网；`source: url` 条目在网络未落地前一律标记"不可用"。

### 5.2 AI 子系统侧（ai_service，TCP 6800）

```
SKILLS LIST                        # 已装 skills
SKILLS INSTALL <skill>             # 从 skills 仓库安装
SKILLS REMOVE <skill>              # 卸载
```

### 5.3 安装本质上是什么

- **安装 = 受控地往 `/modules` 放 `.QD`**（热发现由引擎扫描承担）；
- 包管理不做依赖解析、不引入 APK/DEB 体系（4GB 极端环境扛不住重量级包管理器）；
- 需要什么组件就单独编译源码打包成 `.QD`，需要时放入 `/modules`，不需要时移出。

## 6. 仓库结构

```
/仓库/
├─ <仓库>.qds                    type=index（模块名/来源/版本/校验和；网络阶段增加 source: url）
└─ 实体/                         模块实体存放处（本地仓库的模块本体 + 可选拉取模块预置）
    ├─ <模块>.qd/                install 的拉取源（当前阶段）
    └─ REA.qd/                   可选拉取模块实体（v1.3 预置；install REA 的本地拉取源）
```

- **当前阶段（网络未开始）**：仓库实体 = 本地目录 `/仓库/实体/<模块>.qd`，install 从该目录复制，无网络依赖；
- **网络阶段（路线图阶段 10，与开发文档 §7A.5 对齐）**：仓库索引 `<仓库>.qds` 增加 `source: url` 字段，install 从 URL 拉取；网络未落地前，`source: url` 条目标记"不可用"，install 时明确报错，不得静默失败；
- **远程仓库 URL 索引（阶段 10 前置）**：`repo add <仓库.qds>` 登记的索引可带 `source: https://…`，指向远程仓库镜像；本地 `/仓库/实体/` 作为远程仓库的缓存/预置层——网络拉取的实体落盘到本地实体目录后再复制进 /modules（与"安装 = 受控往 /modules 放 .QD"语义一致）；
- **可选模块实体存放（v1.3）**：REA 等可选拉取模块的实体同样放 `/仓库/实体/REA.qd/`，与系统级模块共用实体目录，仅在索引 `desc`/`kind` 标注"可选拉取"以区分是否进默认镜像；
- 卸载的旧模块可归档到 `/仓库/实体/`（保留存储，不加载）。

## 7. 安全边界与权限闭环

### 7.1 安全边界的定义位置

安全边界在 **`.QDS` 文件**中声明（`security` 段）：

- 模块所需权限声明（如 AI 调用需要眼睛 / 笔 / 橡皮）；
- 模块运行风险级别（只读 / 可写 / 可删 / 可执行系统操作）；
- 隔离要求（是否需要独立容器 / 是否允许访问网络 / 设备）。

### 7.2 声明 ≠ 授权（硬性）

- `.QDS` 里声明的权限只是**请求**，不是生效授权；
- 安装时若模块声明了工具权限，主系统提示用户确认授权（或拒绝仅以骨架模式安装）；
- 运行时：AI 执行该模块时仍受**双域权限开关**约束——用户未授出的眼睛 / 笔 / 橡皮，AI 无对应跨框架能力；
- 授权唯一来源是用户，可随时撤销。

### 7.3 模块运行隔离

- 模块程序以独立进程运行（module-engine fork/exec `entry`），模块崩溃不影响引擎与其他模块；
- 模块间通信经约定通道（模块总线 / 端口转发），禁止直接读写其他模块内部文件；
- 系统级模块（包管理 / 渲染器 / 用户态）与普通应用模块同级管理，但可通过 `security` 声明系统级权限。
