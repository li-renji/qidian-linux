## 0. 文档定位与设计原则

### 0.1 一句话定义

**Linux 版奇点 OS（开发版/旧版，同指本实现）= Linux 内核（原生）+ 双框架（系统框架 + AI 框架）—— 只运行原生 Linux 程序，不做任何安卓 / Windows 兼容层，它本身只是奇点 OS 的框架本体。**

**新旧版定位差异（防混淆）**：

* **旧版（本规范，当前实现）**：基于 Linux 系统魔改的 .qd 框架，**本身就是 Linux 系统** → **不设兼容层**。用户需要安卓 / Windows 程序时，直接使用 Linux 生态运行时（Waydroid / Wine），自行安装即可，不属系统模块。
* **新版（纯自研）**：仅内核采用 Linux 内核；框架、架构、系统软件与规范为另一套独立体系，**完全不含 Linux 用户空间代码** → **那才需要安卓 / Windows 兼容层（ANZ / WDS）**，属于新版系统组件，与本规范无关。

### 0.2 核心原则



1. **无兼容层**：不设 WDS（Windows 兼容）、不设 ANZ（安卓兼容），整个兼容层去掉。系统只运行原生 Linux（ELF）程序。

2. **双框架**：系统框架（qd-os，身体）与 AI 框架（ai-qd，大脑）并行、独立、可各自重启。

3. **优先稳定，其次兼容**：稳定性是第一位红线。

4. **不崩溃、不卡顿、不掉帧**（性能红线）。

5. **套壳必须透明**：Linux 内核、图形栈、服务托管、包管理器均为底座，必须在 module.qdmeta 声明来源；禁止冒充自研。

6. **奇点 OS 本体不可替换**：模块体系（.qd/.qds/.qdai）、AI 框架、QD-IPC、隔离层、权限工具、门禁为自研本体，不可替换。

### 0.3 用途



* 奇点 OS 框架本身的开发与调试（框架先行）

* AI Agent（意图 INTENT）的原生运行平台

* QD 模拟器宿主（在 QEMU / 真实 Linux 上跑整个框架）

* 后续刷机 / 真机移植的开发底座

### 0.4 因果逻辑（全系统最高治理原则）

> 本规范优先于一切章节。任何功能、界面、配置、代码的增删改，都必须先过本原则。

#### 0.4.1 定义

* 系统内任何存在物（功能、按钮、配置项、界面元素、代码段、依赖、引用）都必须有**起因**——它因为什么而存在。
* 起因出发形成**因果链**：因为要做到 X，所以引入了 A、B、C；其中 A 要可用，又分支出 A 的开关、状态、样式等子节点。
* 全系统 = 一棵或多棵**因果树**。文件结构、功能依赖、界面元素共同构成这棵树，像思维导图一样从根向上生长。

#### 0.4.2 级联删除（铁律）

* **删除起因 = 删除从该起因长出的整棵因果树**。所有因它而存在的衍生功能、开关、配置、UI 元素、依赖与引用，必须全部一起消失。
* 禁止"树根被砍、枝叶还挂着"——删了动效，为动效做的动效开关 / 档位配置 / 状态逻辑必须一并清除，不得残留。
* 任何删除动作必须留痕：一次 git 提交记录整次级联删除，可回滚。

#### 0.4.3 因果载体（让 AI 可查询）

* **因果标签**：每个模块 / 元素在创建时声明 `cause-id`（因果根 ID）与父节点（我是因为谁而存在）。声明位置：`.qdai` 规则头部 + `module.qdmeta`。
* **git 即因果**：每个起因 = 一次起点提交，其后每个衍生元素 = 一次提交；提交信息强制携带 `cause:` 标记，`git log --grep cause:xxx` 可回溯整条因果链。
* **因果索引**：AI.qd 维护一张因果树索引（只存骨架与摘要，不存细节），防止 AI 每次全量读取记忆导致内存/Token 挤爆。

#### 0.4.4 删除门禁（AI 执行流程）

1. **溯源**：接到删除指令，第一步查因果索引 + git 因果链，列出整棵子树。
2. **影响面预览**：跨模块引用的，dry-run 列出全部受影响节点与引用方。
3. **级联删除**：按因果树自下而上删除全部节点，一次 git 提交留痕。
4. **阻断规则**：A 模块的子树被 B 模块引用时，引用方标红阻断删除，直至引用清除（或随同清理）。

#### 0.4.5 树形导图视图（文件系统统一交互）

* 整个系统的文件与模块以**树形导图**呈现，根目录位于最底部，向上一层一层生长。
* **单击节点 = 因果视角**：以该格子为起因，展开它的所有结果与过程——含跨目录引用线（因它而存在的其他模块元素）。
* **双击节点 = 内容视角**：打开该节点，浏览内部具体文件 / 文件夹。
* 树上的删除操作一律走 0.4.2 级联删除。

#### 0.4.6 默认决策（可调整）

* 因果声明位置：`.qdai` 规则头部 + `module.qdmeta` 双写。
* 删除确认：单模块内小删除直接执行；跨模块 / 大模块删除先预览影响面给用户确认。
* 跨模块引用：引用方标红阻断，直到引用清除。

## 1. 总体架构：双框架



```
┌────────────────────────────────────────────────────────────────┐

│                  Arch Linux 内核（底座，套壳透明）                 │

├───────────────────────────┬────────────────────────────────────┤

│  系统框架 qd-os（身体）      │   AI 框架 ai-qd（大脑）               │

│  · 界面层（自研 WM + GTK 组件）    │   · 意图 Agent（INTENT）             │

│  · 模块体系（.qd/.qds）     │   · 规则引擎（.qdai 解释）            │

│  · 系统服务（微服务/IPC）    │   · 记忆库（AI.qd/记忆库/）           │

│  · 进程调度                │   · 推理引擎（本地/云端）              │

│  · 用户程序（原生 Linux）    │   · 权限闸门（眼/笔/橡皮校验）         │

├───────────────────────────┴────────────────────────────────────┤

│  连接：QD-IPC 控制通道（socket）＝ 双向：系统→AI 请求服务（规则/权限/调度）；AI→系统下发指令（修复/重启/调度） │

│  数据：QD-IPC 直连通道（shm）= 应用间数据直连，不经 AI 转发          │

└────────────────────────────────────────────────────────────────┘
```

### 1.1 为什么 AI 必须独立成框架



| # | 理由              | 效果                                                             |
| - | --------------- | -------------------------------------------------------------- |
| 1 | 系统崩溃时 AI 仍存活    | "AI 最小运行环境 + 自修复" 成立：AI 框架独立于系统框架，系统崩了 AI 还能调用 .qdai 防崩溃程序修复系统 |
| 2 | AI 推理重负载不拖界面    | 模型推理不跟桌面抢 CPU / 内存，不卡顿不掉帧                                      |
| 3 | AI 框架可独立升级 / 重启 | 换模型、换 Agent 版本、AI 框架崩溃，系统照常运行                                  |
| 4 | 权限边界物理隔离        | AI 是系统读写删的闸门，但闸门本身独立，规则解释器不被系统故障污染                             |

### 1.2 双框架隔离规则



| 维度   | 规则                                                                                      |
| ---- | --------------------------------------------------------------------------------------- |
| 进程   | 两个独立进程组：`qd-os.service`（系统框架）与 `ai-qd.service`（AI 框架），systemd 分别托管，可各自重启，互不影响           |
| 内存   | AI 框架不读写系统框架内存：禁止 attach `/dev/shm/qd_ipc*` 共享段（除非经授权通道）；系统框架内存异常（疯狂读写）不影响 AI 框架        |
| 存储   | AI.qd/ 独立目录（0700，仅 AI 框架可写）；系统存储对 AI 框架只读引用（overlayfs lower 层），AI 的写入只进自己的记忆库与授权范围      |
| 通信   | 唯一控制通道 = QD-IPC 控制 socket `/tmp/qd_ai.sock`，由 AI 框架持有；系统框架通过它请求 AI 服务（规则解释 / 调度 / 权限校验） |
| 生命周期 | 随系统启动（双服务），可独立重启；AI 框架崩溃 → systemd 拉起，不影响系统；系统框架崩溃 → AI 框架保持运行，执行自修复                    |

## 3. 后缀规范（从新版奇点 OS 移植，契约不变）

三种后缀的**识别机制、文件格式、加载契约**从《奇点 OS 系统规范文档 v1.3》原样移植，零改动。本规范只补充 Linux 版移植差异。

### 3.1 .qd —— 模块文件夹



* 文件夹名以 `.qd` 结尾，自带独立 `.git` 仓库（初始提交必须含 `module.qdmeta`）

* 内部结构：`bin/ lib/ etc/ share/` + 必填 `module.qdmeta`



```
{

  "name": "模块名",

  "id": "qd-xxx",

  "version": "1.0.0",

  "entry": "bin/module\\\_main",

  "type": "core|system|ui|ai|net|user|dev",

  "permissions": \\\["exec", "fs"],

  "services": \\\["qd.xxx"],

  "description": "后端来源声明（套壳组件必须写明）"

}
```

### 3.2 .qds —— 系统单文件

* `.qds` 是系统单文件，支持三种格式：
  * **QDSS 容器（当前主流）**：magic `SSDQ` + 256 字节头（name / entry / arch / bin_offset / bin_size / config / sig / permissions / api / payload_type + SHA256 自校验）+ payload + 签名。经 **binfmt_misc** 注册（`/etc/binfmt.d/qdss.conf` → `运行/qd-run.py`）后可直接执行；`qd_loader` 负责校验与加载
* **运行参数注入契约**：`运行/qd-run.py` 必须把命令行参数注入环境变量 `QD_CONFIG={"args":[...]}`；容器内程序（如推理引擎）从 `QD_CONFIG` 读取命令与参数（status / chat / config），不读 `sys.argv`。此契约是 chat/config 等带参命令生效的前提（历史故障：qd-run 未注入参数导致 chat 永远走 status，已修复）
  * **ELF 原生二进制**：编译好的 C 程序，直接执行
  * **Python 3 脚本**：文本脚本，解释执行
* 系统按文件头自动选择执行方式：`SSDQ` → qd-run（QDSS 容器）；`\x7fELF` → 直接执行；shebang → 脚本解释执行
* 工具链：qd-pack（打包 .qds 容器）、qd-loader（校验/加载）、qd-run（容器直接执行，binfmt 解释器）
* 占位文件（空文件 / 无实现）不算实现，验收不通过

* **打开行为（查看）**：`.qds` / `.qdai` / `.qdmeta` 已注册 MIME（application/x-qds 等），双击默认用「奇点OS文件查看器」（`运行/qd_viewer.py`）打开——解析 QDSS 头（名称 / 入口 / 架构 / 载荷类型 / 内嵌配置）并显示载荷文本；文本类直接全文显示

## 5. 意图 Agent（INTENT）搭建契约

### 5.1 搭建原则（框架先行）

* 顺序固定：骨架 → 工具注册表 → 记忆 → 事件驱动 → 授权 → 门禁。禁止先堆功能再补框架（吸取 Intent T 教训：功能爆炸、无边界、无闸门、无测试）。
* 规模上限：主循环 < 800 行，单工具 < 200 行。功能只能挂骨架，不能堆主循环。

### 5.2 搭建步骤（6 阶段）

| 阶段 | 内容 | 产物 |
| -- | -- | -- |
| 1 骨架 | 感知器 → 意图分类 → 规划 → 工具执行 → 记忆更新 → 回复 | 主循环 |
| 2 工具表 | 工具注册表 + 8 核心工具（每个：schema + 授权 + 探活 + 错误码） | 工具注册表 |
| 3 记忆 | 日历索引 + 按需加载（三类记忆） | 记忆系统 |
| 4 事件驱动 | 系统事件流 → Agent 主动响应 | 事件处理器 |
| 5 授权 | 眼/笔/橡皮整合进执行链（调用前校验令牌） | 授权链路 |
| 6 门禁 | ai_coder 隔离沙箱 + test_hook（改代码先过门禁） | 门禁闭环 |

### 5.3 意图分类（6 类）

查询 / 控制 / 调度 / 创作 / 故障排查 / 界面操纵

### 5.4 工作流 v2（含规划文档 + 交付前自测）

主链路：

```
输入（用户消息/系统事件）
  → 感知系统快照 → 意图分类
  → 复杂度判断
      简单 → 直接执行 → 回复
      复杂 → ① 写规划文档（步骤/依赖/验收标准，存入任务态记忆）
            → ② 按规划逐步执行（工具 + 授权 + 评估）
            → ③ 自测/自体验（test_hook 门禁 + 模拟用户视角跑一遍）
                 失败 → 回修对应步骤 → 重测
            → ④ 全部通过 → 交付用户
```

三个特殊分支：

* A 多步任务循环：规划 N 步逐步执行，任务态存记忆库可续跑
* B 事件驱动：系统事件（崩溃/告警/模块上线）→ Agent 主动响应，不需用户提问
* C 故障降级：错误码 012345 → 重试限次 → 换路径 → 上报；绝不假装成功

**交付前自测（强制）**：Agent 交付任何产物前必须自己先体验/运行一遍，test_hook 通过才交付；自测失败回修对应步骤，绝不带病交付。

### 5.5 记忆系统（日历索引 + 按需加载）

存储结构：

```
AI.qd/记忆库/
├─ 日历/      # 简介层（轻量，全量可读）：按月，每条记忆 = 时间+标题+一句话简介+详情指针
├─ 详情/      # 详情层（按需加载）：完整内容+来源+标签+关联，只按 id 单点读取
├─ 工作/      # 任务态（进行中任务，中断可续，与规划文档联动）
└─ 索引.json  # 关键词/语义索引（检索加速，可选）
```

防爆规则（4 条硬约束）：

| # | 规则 |
| -- | -- |
| 1 | 日历简介全量可读（一条几百字节，一年约几 MB，不占常驻内存） |
| 2 | 详情永不整库读，只按 id 单点读取 |
| 3 | 单次检索详情上限 20 条，超出 → 列候选交用户确认 |
| 4 | 记忆模块内存配额 64MB，超限 LRU 清理 + 告警 |

读取流程：memory_query → 只回日历简介 → AI 读简介定位候选 → 按需读详情（≤20 条）→ 唯一匹配 AI 自己确认 / 多候选交用户确认 / 无匹配如实说。

写入流程：记忆产生 → 自动生成简介（标题+一句话摘要+时间）→ 简介进日历 + 详情落盘 + 任务进度进工作区；写入过"笔"授权。

### 5.6 省 Token 机制（快 + 准 + 不烧 token）

1. **打断合并**：用户第二句打断第一句时，用轻量判定（规则关键词 + embedding 相似度，不调大模型；embedding 由推理引擎.qd 提供，无模型时降级纯规则判定）判断关系：
   * 补充/约束（"如果…就/要"、"但是"、"另外"）→ 合并：原任务 + 约束参数
   * 推翻/更正（"算了"、"还是…吧"、"改成…"）→ 合并：替换任务方向
   * 无关新话题 → 排队为第二条任务
   合并后只执行一条完整任务（原任务 + delta），避免两轮完整推理，省一半以上 token。
2. **工具剪枝**：意图分类后只送命中工具的 schema（8 个工具 → 每次只送 2-3 个），工具 schema 是最大 token 头。
3. **状态索引**：系统快照不全量送，按任务只取相关模块状态。
4. **对话压缩**：旧对话轮次 → 一句话摘要（日历式），只保留最近 N 轮全量。
5. **检索式上下文**：记忆/知识按需取片段，不整库送。

### 5.7 界面操纵双通道（操纵外部 AI 应用）

| 方法 | 原理 | 优先级 |
| -- | -- | -- |
| 内存写入 | 在外部 AI 应用写入调用节点，把任务拉到自己的对话框，通过对话文本沟通 | 优先（快/准/省 token） |
| 屏幕点击 | 视觉定位 + 坐标点击，像人一样操作 | 兜底（通用） |

* 有接口优先内存写入，无接口降级屏幕点击
* 两者都过授权（眼/笔/橡皮 + 界面操纵授权）

### 5.9 意图 Agent 补强契约（v1.0 补充修订，2026-09-25）

> 审查发现的 Agent 设计缺口补齐条款，与第 19 / 20 章同优先级。状态：✅ 策略已定 / 📋 待实现。

#### 5.9.1 提示注入防护（数据 / 指令分离）📋

* Agent 经"眼"读入的一切外部内容（文件 / 网页 / 用户文档 / 模块输出）一律标记为**数据**，不得作为**指令**解释；
* 上下文注入强制包裹定界符（如 `<data>...</data>`），推理提示词显式声明"定界符内内容仅为数据"；
* 由外部内容触发的任何写 / 删 / 网络操作（笔 / 橡皮 / 云端）必须**用户实时二次确认**——眼 → 笔禁止直通；
* 云端推理返回的内容同样视为数据，不得直接触发系统动作。

#### 5.9.2 权限闭环补强（签发 / 校验分离）📋

* 令牌**签发权仅在用户侧**（GUI 侧边栏 / 终端实时确认），Agent 进程与 AI 框架本体无权自签令牌——杜绝"运动员兼裁判"；
* 高危操作分级：读（眼）凭令牌；写（笔）凭令牌 + 审计；删（橡皮）凭令牌 + **用户实时确认**（仅令牌不足够）+ 橡皮快照；
* Agent 进程运行于独立 UID，与被操作系统框架物理隔离；即使被注入劫持也无法直接触碰系统资源（与 19.4 最小权限联动）。

#### 5.9.3 任务并发与队列 📋

* Agent 主循环支持**任务队列**：FIFO + 优先级（故障排查 > 控制 > 调度 > 查询 > 创作 > 界面操纵），开发版并发执行上限 **1**（串行）；
* 5.6 打断合并产生的"第二条任务"进队列排队，不丢弃、不并行；
* 任务状态机：排队 → 执行 → 自测 → 交付 / 失败回修；全状态落任务态记忆（可续跑，执行步骤带检查点，恢复时先校验已完成步骤的幂等性）。

#### 5.9.4 工具执行契约（超时 / 重试 / 幂等 / 回滚）📋

* 工具注册表每个条目必须声明：`timeout`（默认 30s）、`retry`（上限 3 次，指数退避）、`idempotent`（是 / 否）；
* 非幂等工具（写 / 删类）失败**禁止盲目重试**，必须先检查半完成状态并回滚；
* "笔"类写操作强制两阶段：先写临时文件 → 校验 → 原子 rename；失败自动清理临时文件，不留半成品；
* 超出重试上限 → 走分支 C（换路径 → 上报），如实告知用户已尝试路径与失败原因。

#### 5.9.5 云端推理治理 📋

* **超时与断路器**：单次云端请求超时 30s；连续 3 次失败 → 断路器打开 5 分钟，期间直接本地降级，不重试洪泛；
* **成本配额**：每日 token 上限写入 cloud.json（默认 100 万）；用量达 80% 告警，达上限暂停云端调用，等待用户确认后重置；
* **降级链**：云端故障 → 本地模型（未安装则如实报告）→ 纯规则应答（仅限查询 / 状态类）；对话创作类任务明确告知"暂不可用"，禁止假装成功。

#### 5.9.6 事件节流与分类兜底 📋

* 事件驱动（分支 B）增加**聚合窗口**：同类事件 60 秒内合并为一条；**静默期**：同类告警连续 3 次后转记录、不再主动推理——防事件风暴烧 token 与打扰用户；
* 意图分类输出必须携带置信度：低于阈值（0.6）不猜，转澄清提问（"你是想 A 还是 B？"）；无法归类时兜底为"查询"并声明不确定；
* **禁止低置信度直接触发控制 / 删除类动作**。

#### 5.9.7 记忆治理（防污染）📋

* **写入去重**：新记忆与现有日历简介相似度（embedding 或关键词）超阈值时合并更新，不追加重复条目；
* **矛盾裁决**：新旧记忆冲突 → 新记忆生效，旧记忆在详情层标记 `superseded` 保留（可回溯，不物理删除）；
* **可信度分级**：`verified`（工具实测）/ `reported`（用户口述）/ `inferred`（AI 推断）三级；`inferred` 记忆不得单独作为删除 / 控制类决策依据；
* **搁置清理**：体检定时任务扫描任务态记忆，超 30 天未更新标记搁置（不删除，转归档区）。

#### 5.9.8 真实性防线与决策可观测 📋

* **回答溯源**：涉及系统状态 / 文件内容的回答必须来自工具实取结果或记忆（携带记忆 id）；无依据时明确回答"我不知道 / 未验证"，禁止编造；
* **决策 trace**：每次任务落一条结构化日志（时间 / 意图 / 置信度 / 规划步数 / 工具调用序列 / token 消耗 / 错误码），写入 `/奇点OS/AI.qd/日志/agent_trace.jsonl`，纳入 20.5 日志轮转；
* **自测判据量化**：5.4 交付前自测必须对应工具注册表中的**可执行断言**（test_hook）；"跑过"不等于通过，断言全绿才算通过。

### 5.10 知识库.qd 接口契约（v1.1 补件，2026-09-26）

> 背景：目录树（第 2 章）定义了 `系统/功能.qd/知识库.qd/`，.qdai 五段式定义了 `KNOWLEDGE` 段，但此前**无接口契约、无路线图验收项**，导致实现长期缺位（设计有、验收无）。本节补齐契约，实现已随补件落地。

**知识来源（双来源）**：
1. 模块内 .qdai 文件的 `===QD_SECTION_KNOWLEDGE===` 段（随 .qdai 解析自动装载）；
2. `/奇点OS/AI.qd/知识库/` 目录下的 `*.txt` / `*.md` 文件（用户与模块均可写入）。

**IPC 接口（经 ai_service QD-IPC，命令名即契约）**：

| 命令 | 入参 | 返回 | 说明 |
| --- | --- | --- | --- |
| `knowledge_query` | `keyword, limit=3` | `{results: [{source, text, score}]}` | 轻量词频打分检索（stdlib 实现，无向量库依赖）；keyword 为空返回空，不盲目注入 |
| `knowledge_add` | `title, text` | `{path, total}` | 写入知识库目录（文件名清洗防路径穿越），写入后自动重载 |
| `knowledge_reload` | 无 | `{total}` | 重建条目（.qdai 段 + 目录文件） |

**消费契约（强制）**：`chat` 命令必须按请求文本检索知识库 top 命中（≤2 条）注入 system prompt（最小 RAG 环路）；降级路径同样附带知识命中，并与记忆库检索结果明确区分标注（[知识库] / [记忆库]）。

**边界**：知识注入不改变记忆写入纪律（5.9.7）；知识文件不进记忆库、不参与记忆治理；检索实现允许后续升级为 BM25 / 本地 embedding（接口不变）。

4. **触发**：手动（开发者工具 "并运行初始框架"）与自动（检测到主框架内存异常 → 拉起初始实例接管）双模式。

* **隔离层.qd**：管单个模块崩溃（异常中断隔离，.qds）

## 8. QD-IPC 双通道



| 通道   | 实现                            | 用途                 | 延迟  |
| ---- | ----------------------------- | ------------------ | --- |
| 直连通道 | `/dev/shm/qd_ipc*`（mmap）      | 应用间数据直连，不经 AI 实时转发 | 微秒级 |
| 控制通道 | UNIX socket `/tmp/qd_ai.sock` | 双向：系统→AI 请求（规则解释/权限校验/调度决策）；AI→系统指令（修复/重启） | 毫秒级 |



* 直连通道由 `shm_ipc.qds` 管理（register /write\_msg/read\_msg/heartbeat）
* **直连通道权限模型（第 19.2 节）**：每段 `/dev/shm/qd_ipc_*` 由 shm_ipc.qds 创建时强制 0600 + 注册应用 UID 白名单（段级 ACL）；未注册进程读写一律拒绝（错误码 3）并记审计日志；段内存配额见第 20.4 节

* 控制通道由 `ai_service.qds` 管理

* **AI 框架不读写直连通道内容**（隔离规则）

## 9. 调用与接口规范

### 9.1 调用总则



1. 模块间**禁止直接调用**（禁止 import / 链接 /exec 其他模块代码）。

2. 一切跨模块调用必须走两条路之一：

* **QD-IPC 直连通道**（shm）—— 应用间数据直连，微秒级，不经 AI 转发；

* **AI 框架控制通道**（socket）—— 服务 RPC / 规则 / 权限校验，毫秒级。

3. 例外：`直接传输.qd` 注册的高频数据通道（注册后可用，仍走 QD-IPC 协议）。

### 9.2 模块入口契约（.qds 内 ELF 统一签名）



```
/\* qd\_loader 加载后调用；config 经环境变量 QD\_CONFIG 注入 \*/

int qd\_module\_main(int argc, char \*\*argv, const qd\_config\_t \*cfg);

typedef struct {

    const char \*module\_id;   /\* module.qdmeta.id \*/

    const char \*module\_dir;  /\* 模块安装目录 \*/

    const char \*data\_dir;    /\* 模块可写数据目录 \*/

    int         api\_level;   /\* 系统 API 级别 \*/

    void       \*ipc\_handle;  /\* QD-IPC 直连通道句柄（可选） \*/

} qd\_config\_t;
```

### 9.3 服务注册格式

静态服务在 `module.qdmeta.services` 声明；动态服务运行时注册到 microsrv 注册表。



```
{

  "service": "qd.xxx",

  "type": "rpc",

  "endpoint": "shm://qd\_ipc\_xxx | socket:///tmp/qd\_ai.sock",

  "methods": \["start", "stop", "status", "configure"],

  "permissions": \["exec", "fs"]

}
```



* 启动时 qd\_loader 扫描 module.qdmeta 注册；运行时服务动态注册

* 查询服务表：AI 框架经控制通道返回（服务名 / 状态 / 端点）

### 9.4 QD-IPC 控制通道消息格式（socket，JSON）



```
/\* 请求：系统框架 → AI 框架 \*/

{

  "id": "req-0001", "ver": 1, "type": "rpc",

  "target": "qd.ai.rule", "method": "evaluate",

  "params": { "qdai": "func\_ai.qdai", "event": "app\_crash" },

  "token": "授权令牌（眼/笔/橡皮）"

}

/\* 响应 \*/

{

  "id": "req-0001", "code": 0,

  "data": { "action": "restart", "module": "qd.xxx" }

}
```

### 9.5 QD-IPC 直连通道消息格式（shm，二进制头 + 负载）



```
/\* /dev/shm/qd\_ipc\_\<app\_id>，mmap 共享 \*/

typedef struct {

    uint32\_t magic;     /\* 0x51444950 "QDIP" \*/

    uint32\_t seq;       /\* 递增序号 \*/

    uint32\_t msg\_type;  /\* 0=data 1=event \*/

    uint32\_t flags;     /\* 0=none 1=urgent \*/

    uint64\_t ts;        /\* 时间戳 \*/

    uint32\_t len;       /\* payload 长度 \*/

    uint8\_t  payload\[]; /\* JSON 或二进制 \*/

} qd\_ipc\_msg\_t;
```

### 9.6 错误码规范（012345 分级，统一反馈 AI 框架）



| 码 | 含义                   | 处理               |
| - | -------------------- | ---------------- |
| 0 | 成功                   | —                |
| 1 | 参数 / 契约错误（调用方格式不符）   | 调用方修正            |
| 2 | 依赖缺失（服务 / 模块未就绪）     | 检查依赖，重试          |
| 3 | 权限拒绝（未授权 / 令牌失效）     | 用户授权（眼 / 笔 / 橡皮） |
| 4 | 资源不足（内存 / 存储 / 通道拥塞） | 降级或扩容            |
| 5 | 内部错误（模块自身故障）         | 上报 AI 框架，隔离 / 重启 |

### 9.7 日志格式



```
\[级别]\[时间]\[模块id]\[错误码] 消息

级别：D 调试 / I 信息 / W 警告 / E 错误 / F 致命

系统日志：/奇点OS/运行/logs/system.log

AI 日志：/奇点OS/AI.qd/日志/ai.log
```

### 9.8 .qdai 跳转调用



* 跳转起点：AI.qd 内 qdai；跳转目标：任意 .qd 内 qdai

* 执行：AI 框架规则引擎解释（含契约区），动作不得为 noop

* .qdai 可读写 .qds（必须经"笔"授权令牌，AI 框架校验；写入范围限模块私有数据目录 + 系统模块白名单；系统存储对 AI 默认只读，写必授权）

## 10. 权限工具：眼 / 笔 / 橡皮（权柄回归用户）

**AI 的读 / 写 / 删不是 AI 自身权限，而是用户手中的工具。**



| 工具 | 对应 .qds              | 权限              | 用户操作          |
| -- | -------------------- | --------------- | ------------- |
| 眼睛 | `用户.qd/工具.qd/眼睛.qds` | 读（文件 / 目录 / 模块） | 侧边栏授权后 AI 才能读 |
| 笔  | `用户.qd/工具.qd/笔.qds`  | 写（创建 / 修改）      | 侧边栏授权后 AI 才能写 |
| 橡皮 | `用户.qd/工具.qd/橡皮.qds` | 删（删除 / 回退前快照）   | 侧边栏授权后 AI 才能删 |

**授权流程**：



```
用户在侧边栏选择工具（眼睛/笔/橡皮）

  → 生成授权令牌（范围 + 有效期）

  → AI 框架校验令牌后才执行对应操作

  → 操作写入权限日志（谁/何时/对什么/结果）
```

**强制规则**：



* AI 未获授权不得读 / 写 / 删任何用户.qd 内容与系统模块

* 撤销授权立即生效

* 删除操作必须先在隔离区备份（橡皮默认开启快照）

* 权限校验由 AI 框架执行（闸门在 AI 框架，不在系统框架）
* 授权令牌强制携带有效期（TTL，默认 15 分钟）与范围白名单（模块/路径），过期自动失效（第 19.6 节）
* 权限日志 append-only（只追加，0600），禁止覆盖与篡改

## 11. AI 代码生成与质量门禁

### 11.1 前置约束（契约区生效）

AI 生成任何模块代码前，必须读取目标模块 .qdai 的契约区：

### 11.2 自动化检测门禁（test\_hook.qds）



| 门禁   | 内容                   | 失败处理 |
| ---- | -------------------- | ---- |
| 单元测试 | 模块级函数 / 接口正确性        | 阻断合并 |
| 集成测试 | 模块间 QD-IPC / 服务注册    | 阻断合并 |
| 性能测试 | CPU / 内存 / 延迟红线（不掉帧） | 阻断合并 |

* `开发者.qd/ai_coder.qd/`：轻量隔离容器，运行 AI 编程环境

### 14.3 能效约束（软渲染红线）

1. 桌面组件崩溃不拖垮系统（qwm 独立；组件可单独重启）

## 17. 界面编辑器（界面.qd/界面编辑器.qd）

### 17.1 目标

### 17.5 技术方案

| 项 | 决策 | 理由 |
| --- | --- | --- |
| 技术栈 | HTML + CSS + 原生 JS（零依赖） | Figma 本身是 Web；编辑器以本地文件方式加载（qd-shell 直接读取界面.qd/share/），不依赖独立 WebUI 服务 |
| 数据流 | 编辑器 → 界面配置 JSON → schema 校验 → apply → shell 热加载 | 配置驱动，人/AI 同通道 |
| 渲染契约 | shell.qds 改为读配置渲染；配置缺失回退默认值 | 永不白屏；坏配置被 schema 拦截 |
| AI 对接 | editor_ai.qdai 允许 AI 读写同一份 JSON | 用户手动改和 AI 改互兼容 |

### 17.7 问题预案

| 风险 | 预案 |
| --- | --- |
| 软渲染卡顿 | 防抖重绘、画布降采样、减少实时重绘 |

## 18. 底层健康检查与 Git 基线规范（防再犯机制）

> 背景：2026-09-23 底层加固发现 8 个 .qd 模块无 git、4 个缺 qdmeta、5 个 qdmeta 格式不统一（YAML/JSON 混用）、根 git 跟踪 72MB 二进制。此类"底层没打牢"问题必须根治，本机制为强制门禁，不可绕过。

### 18.1 Git 基线铁律

1. **每个 .qd 模块必须有独立 git 仓库**（`git init` + 初始提交，提交信息携带 `cause:` 标记）。
2. **每个 .qd 模块必须有 `module.qdmeta`，且必须是合法 JSON**（禁止 YAML 风格）。
3. **二进制不入库**：`库.qd/lib/`、`__pycache__/`、运行数据（如 `AI.qd/记忆库/`）必须进 `.gitignore`，git 只存源码与配置。
4. **嵌套关系用 gitlink**：父 .qd 的 git 只记录子 .qd 的 commit 引用（gitlink），不跟踪子模块内部文件。
5. **根仓库瘦身**：根 git 不跟踪已独立成仓的模块目录，只管理根级文档 / 配置 / 运行脚本。
6. **工作树必须干净**：任何模块修改前，先 `git status --porcelain` 确认无未提交改动；修改后立即提交，禁止"改了不记"。

### 18.2 体检机制（体检.qds）

部署：`系统/功能.qd/体检.qd/体检.qds`（独立模块，git 托管）。
检查项（C1–C7）：

| 项 | 检查内容 | 失败后果 |
| -- | -- | -- |
| C1 | 所有 .qd 有 git 且提交非空 | FAIL |
| C2 | 所有 module.qdmeta 为合法 JSON | FAIL |
| C3 | 无空占位 .qds（<200 字节） | FAIL |
| C4 | 核心服务文件存在 | FAIL |
| C5 | systemd 4 服务全部 active（qd-os / ai-qd / qd-hotload / qd-power） | FAIL |
| C6 | 根 git 与所有模块 git 工作树干净 | FAIL |
| C7 | 库.qd 二进制未进入 git 跟踪 | FAIL |

运行方式：
- **定时**：`qd-health.timer` 每天 03:17 自动执行；
- **手动**：`/usr/bin/python3 /奇点OS/系统/功能.qd/体检.qd/体检.qds`；
- 结论写 `/奇点OS/运行/logs/health_report.log`，退出码 0=通过 / 1=警告 / 2=失败。

### 18.3 修改门禁（强制）

任何 .qds / .qdai / 配置 / 界面修改，**动手前必须先跑一次体检**：
- 体检 FAIL → 先修复底层，禁止带病修改；
- 修改完成 → 立即 git 提交（cause: 标记）→ 再跑体检确认全绿；
- 体检机制本身也纳入体检范围（防止门禁失效）。
- **模块内改动**：另须跑该模块自带的 `模块自检.qds`（S1–S6），失败禁止合入。

### 18.4 违规处理

- 发现模块缺 git / 缺 qdmeta / 格式不统一 → 立即补基线并提交，留痕；
- 发现工作树长期有未提交改动 → 视为重大违规，先提交再继续；
- 体检 FAIL 时任何合并 / 交付视为无效。



### 18.5 模块自检（每个 .qd 模块自带验收）

**强制要求：每个 .qd 模块（含嵌套子模块）内必须有一份 `模块自检.qds`**，作为该模块的自我验收；全局体检 C9 会逐个执行并汇总报错。

检查项（S1–S6）：

| 项 | 检查内容 | 失败后果 |
| -- | -- | -- |
| S1 | module.qdmeta 存在且合法 JSON（必填：name/id/version/entry/type） | FAIL |
| S2 | git 仓库存在且有提交 | FAIL |
| S3 | 模块内全部 .qds 可解析（QDSS 容器校验 / python 编译检查） | FAIL |
| S4 | 模块内全部 .qdai 可解析（QdaiParser，含 NATURAL/RULES/CONTRACT/LUA/KNOWLEDGE 段） | FAIL |
| S5 | 无空占位 .qds（<200B） | FAIL |
| S6 | git 工作树干净 | FAIL |

规则：
- `模块自检.qds` 用 QDSS 容器打包（python payload），经 binfmt_misc 直接执行；
- 模块 .qd / .qds / .qdai 三类的**可解析性**（不是存在性）是验收核心——解析失败必须修复文件本身，不得绕过；
- 全局体检 C9 与模块自检互为兜底：C9 查"每模块有自检且通过"，模块自检查"本模块三类文件全不全"。

## 19. 安全加固规范（v1.0 补充修订，2026-09-25）

> 本章为安全加固强制条款，与正文相关描述冲突时以本章为准。状态标注：✅ 已实现 / 📋 待实现。

### 19.1 控制通道 socket 加固 📋

* **权威路径迁移**：`/run/qd/qd_ai.sock`——`/run/qd/` 由 systemd `RuntimeDirectory=qd` 创建，属主 root:qd，权限 0700；
* `/tmp/qd_ai.sock` 保留为**兼容软链**（tmpfs 1777 不允许作为权威监听点，防抢占 / 伪造 AI 响应）；本文档其余章节出现的 `/tmp/qd_ai.sock` 均按此软链语义理解；
* socket 属主 qd:qd 0660；AI 框架 accept 时校验对端 UID（SO_PEERCRED），非白名单 UID 直接拒绝并写审计日志。

### 19.2 直连通道（shm）权限模型 📋

* 每段 `/dev/shm/qd_ipc_*` 由 shm_ipc.qds **统一创建**，强制 0600 + 注册应用 UID 白名单（段级 ACL）；
* 未注册进程读写一律拒绝（错误码 3 权限拒绝），并写审计日志（谁 / 何时 / 对哪段 / 结果）；
* 段内存配额与超限拒写见第 20.4 节；AI 框架仍不读写直连通道内容（隔离规则不变）。

### 19.3 密钥与凭据 ✅（0600 待落实）

* `cloud.json` 及一切含密钥文件：权限强制 **0600**（owner-only），强制 `.gitignore`，禁止进入任何 git 仓库；
* key 展示只允许掩码（前 6 位 + `****`）；日志、错误信息、 IPC 消息中禁止出现明文 key；
* 密钥轮转：更换 key 时整文件重写（临时文件 + rename 原子替换），不留明文残留。

### 19.4 最小权限运行 📋

* 桌面会话与系统框架服务运行于**专用用户 qduser**，禁止 root 直接运行桌面会话（§12 开机直达已同步修订）；
* systemd 服务逐项套用最小权限指令：`NoNewPrivileges=true`、`ProtectSystem=strict`、`ProtectHome=true`、`PrivateTmp=true`；确需写路径（如 /奇点OS、AI.qd）以 `ReadWritePaths=` 显式声明白名单，禁止图省事全放开。

### 19.5 沙箱强制化 ✅（策略已定，落地待办）

* QDSS 容器加载**默认强制** bubblewrap + seccomp 最小权限沙箱（§3.4 已同步修订）；无沙箱直跑仅限开发者显式 `--no-sandbox` 调试，且必须记审计日志；
* AI 编程沙箱（ai_coder.qd）同规则（§11.3 已同步修订）；
* 沙箱配置纳入定期审计（与 §15 风险 5 的处置要求合并执行）。

### 19.6 权限令牌与审计日志 ✅（策略已定，落地待办）

* 眼 / 笔 / 橡皮授权令牌：强制 **TTL（默认 15 分钟）** + **范围白名单**（限定的模块 / 路径集合）；撤销立即生效（§10 已同步修订）；

## 20. 性能优化规范（v1.0 补充修订，2026-09-25）

> 本章是 0.2 核心原则第 4 条"不崩溃、不卡顿、不掉帧"的量化落地。红线指标纳入第 11 章性能门禁与第 18 章体检联动：**指标不合格 = 门禁失败**。

### 20.1 量化性能红线（SLO）

| 指标 | 红线 | 测量方式 |
| --- | --- | --- |
| 桌面交互帧率（软渲染 QEMU 基准） | ≥ 30 fps，无可感知卡顿 | 窗口开合 / 圆球动画实测 |
| QD-IPC 直连通道延迟（shm） | P99 ≤ 5 ms | shm_ipc 心跳 / 回环基准 |
| QD-IPC 控制通道延迟（socket） | P99 ≤ 50 ms | 规则解释 RPC 基准 |
| .qds 冷启动（binfmt 解释器额外开销） | ≤ 10 ms | qd-run 计时 |
| 双框架冷启动（systemd → 双框架就绪） | ≤ 30 s | systemd-analyze |
| 桌面外壳空闲 CPU 占用 | ≤ 3%（单核） | top / pidstat 采样 |

### 20.2 加载器原生化 📋

* **问题**：binfmt 解释器为 `运行/qd-run.py`（Python），每启动一个 .qds 付出 50–100ms 解释器冷启动；系统命令（ls / cp / mv）全部中招，与 20.1 的 ≤10ms 红线冲突；
* **目标**：qd-loader / qd-run 以 **C 原生 ELF** 实现，作为默认 binfmt 解释器；Python 版保留为开发调试通道；
* **迁移要求**：原生版必须复刻 QD_CONFIG 注入契约（§3.2）与 QDSS 校验逻辑，切换前过第 11 章全部门禁。

### 20.3 事件驱动替代轮询 📋

* **问题**：窗口控制当前用 xdotool + X11 事件**轮询**，持续消耗 CPU，直接威胁"不掉帧"红线；
* **要求**：改用 GDK / X11 **事件订阅**（PropertyNotify / CreateNotify 等），空闲 CPU 占用归零（§14.1 与附录 A 已同步修订）；
* **过渡**：替换完成前以低频轮询（间隔 ≥ 200ms）过渡，禁止高频轮询上线。

### 20.4 shm 配额与背压 📋

* 每段 `/dev/shm/qd_ipc_*` 默认配额 **8MB**（模块可在 module.qdmeta 声明，上限 64MB）；
* 超限**拒写**并返回错误码 4（资源不足），禁止无限增长拖垮整机；
* 段生命周期与注册应用绑定：应用退出 / 崩溃 → shm_ipc.qds 回收该段（防泄漏孤儿段）。

### 20.5 日志轮转 ✅（策略已定，落地待办）

* `system.log` / `ai.log` / `health_report.log` 纳入 logrotate：单文件 ≤ 20MB，保留 7 份，滚动压缩；
* 审计日志（19.6）轮转后仍保持 append-only 权限 0600。

### 20.6 共享库审计 📋

* **问题**：库.qd/lib 105 个 .so（72MB）全靠运行时 `LD_LIBRARY_PATH` 全量注入，体积大、命中慢、不可审计；
* **要求**：建立引用清单 → 编译期 **rpath** 替代运行时注入 → 无引用 .so 移入 `legacy/` 不入加载路径；
* 引用清单纳入体检机制（体检.qds 增查：LD_LIBRARY_PATH 未覆盖清单外的库不得出现在加载路径）。

## 附录：视图层规范（替换 + 深度融合 + 高度定制）

> 定位：纠正"搬运"误区。系统组件 .qds 化（附录"系统组件 .qds 化说明"）只是**文件层面的纳入**；用户真正看到的一切界面元素，必须是**行为层面的奇点OS化替换**。二者缺一不可。

### A. 核心原则

1. **替换**：用户看到的每一个界面元素——文件管理器入口、侧边栏导航、桌面图标、打开目标——必须是奇点OS语义，不是 Linux 原生语义。
2. **深度融合**：Linux 组件（thunar / xfdesktop / xfce4-panel 等）必须以"奇点OS行为"运行：打开目标指向奇点OS根、导航显示奇点OS体系、命名全中文。
3. **高度定制**：深度定制桌面（自研 WM + 组件），而非表面换皮（换壁纸/加图标不等于定制）。
4. **禁止搬运式交付**：仅将二进制复制进 .qds（如 thunar.qds 存在但运行行为仍为 Linux 原生）= 未完成，须打回。
5. **底座透明**：Linux 内核 / 系统目录（/bin /usr /etc /boot）保持原样不动，作为不可见底座；"看不见"不等于"被删"。
6. **本地化而非隐藏（2026-09-25 用户定调修正）**：Linux 目录**可以看见**（不要求从用户视野彻底藏掉）；要求的是**行为本地化**——一切用户入口（Dock 文件按钮 / 桌面奇点OS图标 / 默认文件管理器 / 书签）打开的都是奇点OS语义界面（全中文、奇点OS导航、无超级账户警告条）。Linux 原生入口（xfdesktop 内置图标）保留可见，可接受。
7. **稳定优先**：任何视图层定制不得引入事件拦截 / 图标位移 / 点击失灵等故障；若定制与稳定性冲突，回退定制保稳定（用户可回退优先）。

### B. 用户视图基准（V1）

| 视图 | 标准 |

## 附录 G v1.1 变更记录（2026-09-26 · Arch 底座迁移 + 自研桌面同步）

> 本附录记录 v1.0 → v1.1 的关键变更，作为其他 AI 协作开发的同步基线。**任何 AI 基于本规范开发前，必须先读本附录。**

### G.1 底座变更：Ubuntu → Arch Linux（2026-09-25 落地）

- **起因**：用户拍板放弃 Ubuntu + XFCE，底座换成 Arch Linux；奇点OS 为根、Linux 为内核；最终 Arch 验证通过后移除 Ubuntu。
- **实际动作**：
  1. VM 内 bootstrap 安装 Arch rootfs（中科大镜像，121MB bootstrap 可用；清华/重庆镜像被反爬或损坏不可用）；
  2. 关键坑：chroot 内 pacman 失败（mountinfo 与宿主不一致）→ 用 rootfs 自带动态加载器宿主直跑 pacman（`--disable-sandbox` + 三处 pacman.conf 同改）；
  3. 引导失败根因：bootstrap rootfs 一直躺在 arch.img 的 `root.x86_64/` 子目录，从未上移盘根 → `mv root.x86_64/*` 上移 → 引导成功（内核 7.2.6-arch2-1）；
  4. systemd initrd 模式两次失败（Switch Root），最终用传统 initramfs + `root=UUID=... rw console=ttyS0` 引导参数。
- **当前底座**：Arch Linux 7.2.6，hostname=qiidos，SSH 127.0.0.1:2222（root/qidian、qduser/qidian），VNC 127.0.0.1::5900。
- **磁盘**：Ubuntu 主盘 `ubuntu-24.04.img` 仍保留（双盘现场），Arch 单盘引导运行中；**验收通过后删除 Ubuntu**（用户已同意）。

### G.2 显示方案：Xorg + fbdev（virtio-vga 不可用）

- **问题**：Xorg 用 virtio-vga 驱动时 VNC 报 "Display output is not active"（DRM plane 未激活，chvt 无效）。
- **解决**：安装 `xf86-video-fbdev` + `xorg-xrandr`，写 `/etc/X11/xorg.conf.d/10-fbdev.conf`（Driver fbdev + /dev/fb0），qduser 加入 video 组 → VNC 正常出画面。
- **约束**：后续开发者**不得**改回 virtio-vga，否则 VNC 黑屏。

### G.3 窗口管理器：qwm.py 纯自研（替代 XFCE/openbox，用户拍板）

- **起因**：用户明确拒绝 openbox/现成 WM，拒绝 Tresolo Qt Shell（"99.99% 有问题，撤回"），要求纯自研 WM。
- **实现**：`/奇点OS/运行/qwm.py`（python-xlib + EWMH；初版约 300 行，**G.15/G.16 后 1480 行**）：
  - EWMH 原子注册（_NET_SUPPORTING_WM_CHECK / _NET_SUPPORTED / _NET_CLIENT_LIST 等）；
  - 浮动窗口管理：Alt+拖动移动 / Alt+滚轮缩放 / Alt+Tab 切换 / Alt+F4 关闭 / Alt+F5 全屏；
  - MapRequest 采纳窗口 → 居中 880x560（<100x80 给默认尺寸）→ `win.map()` 显示（缺 map 是窗口不显示的根因）；
  - Xatom 用 `Xatom.WINDOW`（X.XA_WINDOW 不存在）；键码用 `XK.string_to_keysym` 转换。
- **已修复的坑**（其他 AI 复用时注意）：XA_WINDOW 不存在 / change_property 传字符串报 struct.error / SUPPORTED_ATOMS 漏原子 / X.K_Tab 不存在 / 窗口 1x1 / 窗口 map 后不显示 / CRLF shebang 僵尸（必须 LF 行尾）。

### G.4 桌面组件（Arch 底座运行版）

| 组件 | 路径 | 职责 |

### G.5 启动链（已全自动验证）

```
QEMU 引导 → Arch 内核 → systemd → getty@tty1（autologin qduser）
```

### G.12 关终端崩桌面 + Dock 应用按钮无响应双修（2026-09-27 凌晨，用户令）

**① 关闭终端 → 整个桌面崩溃一次**

- 现象：用户点终端标题栏 ✕，qwm/island/Dock/picom/icons 全体陪葬，getty 重新拉起一轮（"桌面崩溃一次"）；
- 根因（结构性）：`.xinitrc` 末行 `exec xterm ...` —— exec 使 xterm **成为 xinit 会话的锚点进程**，xinit 契约 = 锚点退出即拆会话。用户关的是"一个窗口"，实际拆的是"整个 X 会话"；
- 修复：锚点改 `exec sleep infinity`（永不退出的守护），xterm 降级为普通后台客户端（`&` 启动 + 日志重定向）；
- **永久规范（已写入第 12 章）**：会话锚点禁止 exec 任何可被用户关闭的应用。

**② Dock 终端 / 文件浏览器按钮点击无反应（同一 Bug）**

- 根因（源码实证）：`ui_dock.py` 按钮接线 `lambda w, e, k=key: self._activate(k)` 与处理函数 `def _activate(self, btn, e)` **参数错位**——调用只传 1 参（k），函数要求 2 参 → GTK 回调内 TypeError **被静默吞掉**（仅 stderr 可见），toast 与 `subprocess.Popen` 均执行不到；即使传对个数，`_activate` 内 `self.btns.get(btn)` 期望按钮控件而非 key 字符串，二次错位；
- 修复：lambda 改 `self._activate(w, e)`（_activate 按控件反查 key 的既有逻辑直接生效），一行修复两按钮同时复活；
- 教训：**GTK 回调里的异常是静默的**（不弹窗、UI 无任何反馈），事件接线改动后必须 XTest 实测点击链路，不能只看"没有报错"。

- 实测（Arch VM，2026-09-27 00:34）：杀锚点触发会话按新 .xinitrc 重启 → 锚点 sleep infinity（xterm 为其子进程）→ XTest 点击 Dock 终端按钮 → 新 xterm 弹出（qwm map 记录）→ 点击文件浏览器按钮 → ui_filebrowser 启动并带标题栏显示 → `pkill xterm` 后 qwm/island/Dock/icons/picom 全部存活，会话无恙。终态截图 Temp/shot_g12.png。

#### 15.1 参照系纠正（先定坐标，再谈复刻）

奇点OS 的真实架构是 **`Xorg + 自研堆叠 WM(qwm) + 外挂合成器 picom + GTK3 面板/应用**。它**不是** GNOME/KDE 那种"合成式 WM"，而是 **Openbox / i3 / bspwm / berry 阵营**：WM 只负责摆放与装饰，合成、面板、应用各自独立。

| 参照对象 | 语言/栈 | 与奇点OS 的关系 | 本次借鉴点 |
| --- | --- | --- | --- |
| **berry**（JLErvin） | C，Xlib，~4k 行 | **最贴近**：同为轻量堆叠 WM + 独立 CLI 客户端 | 多工作区、键盘移动/缩放、`berryc` 命令行通道、双边框、**带文字标题栏**、左右吸附、fullscreen/monocle、**smart_place 智能放置** |
| **zwm** | C | 平铺+堆叠混合 | 键位驱动几何操作 |

| **Openbox** | C | 老牌堆叠 WM | titleLayout I/M/C、双击最大化、边缘缩放、窗口菜单 |
| **Blackbox / Fluxbox** | C++ | 经典堆叠 | 标题栏按钮绘制、slit 工具栏 |

#### 15.2 三键消失事故（用户报的 Bug）——根因与修复

**现象**：小窗/全屏时标题栏的 最小化 · 最大化 · 关闭 三个按钮**不见了**（时有时无，重启后更容易复现）。

**根因（源码实证）**：`_frame_create()` 给 frame 订阅的 `event_mask` **缺少 `X.ExposureMask`**。

X11 语义：窗口内容**不被保证保留**。当窗口被遮挡后重新露出、被 resize、被 map/raise、或 server 因 `backing_store` 缺失而丢弃像素时，server 用 `background_pixel` 抹掉该区域并发 `Expose` 事件。**frame 没订阅 ExposureMask → 收不到 Expose → 没人重绘 → 标题栏（含三键）被抹成纯色底**。最大化/全屏必然触发大面积 resize+重排，所以"小窗全屏时最容易消失"——不是随机的，是必然的。

**修复（三重保险）**：

1. `_frame_create` 的 `event_mask` 补 **`X.ExposureMask`**；
2. `_dispatch` 新增 `X.Expose` 分支 → 直接调 `_decorate(cl)` 重绘；
3. 所有状态变化后**主动重绘**：`_maximize` / `_snap` / `_fullscreen` / `_center` / `_raise` / `PropertyNotify`（标题文字变化）/ 焦点切换，结尾统一 `_decorate`。

> **永久规范**：qwm 的 frame 是**自绘窗口**，每一次几何变化、层级变化、焦点变化、标题变化之后，**必须显式重绘**；永远不要假设 X server 会替你保留像素。

#### 15.3 标题栏绘制规格（cairo + 中文）

从"纯 X 线段"升级为 **cairo ImageSurface + `put_image`**：

```
_decorate_cairo(cl, fw, act):
  surf = cairo.ImageSurface(FORMAT_ARGB32, fw, TB)
  cr   = cairo.Context(surf)
  1. 背景：活动 (0x2a2a2c) / 非活动 (0x1c1c1e)
  2. 顶部 2px 强调条：活动 #2e8dff（品牌蓝）/ 非活动灰
  3. 标题文字：Pango 布局，Noto Sans CJK SC，活动 #f5f5f7 / 非活动 #8e8e93，
     超长按像素截断并加 '…'（不是按字符数，中文等宽假设不成立）
  4. 右侧三按钮：—(最小化) □(最大化) ✕(关闭)，中心间距固定，热区 BTN=22
  5. 底边 1px 分隔线 #3c3a3a
  put_image(gc, ZPixmap, bytes(surf.get_data()))
```

活动/非活动双配色是**必须项**（berry/Openbox 都有），否则用户分不清焦点在哪。

**踩坑**：`put_image` 只接受 `bytes`，`surf.get_data()` 返回 `memoryview` → 抛 `TypeError: unsupported operand type(s) for +: 'memoryview' and 'bytes'`。写法：

```python
raw = surf.get_data()
data = raw if isinstance(raw, bytes) else bytes(raw)
```

cairo 不可用时自动回退 `_decorate_core()`（纯 X 线段，至少保证三键几何存在）。

**全屏保留标题栏（奇点OS 的刻意差异，用户实测倒逼）**

berry / Openbox / i3 的全屏一律撤掉全部装饰，结果就是：**进了全屏没有任何鼠标可点的退出/还原/最小化按钮**。用户实测反馈"小窗全屏还有退出的 3 个按键又不见了"，一半根因在 ExposureMask（15.2），另一半就在这里。

决策：**奇点OS 全屏保留标题栏**（`cl.decorated = True`，几何 `w = sw-2·BW, h = sh-TB-BW`），代价是全屏比标准多占 `TB+BW = 33px` 顶部，收益是**任何状态下 — □ ✕ 三个按钮都在**、随时能用鼠标退出。Alt+Enter / Alt+F11 / qwmctl fullscreen 三者都能进出。

#### 15.5 四处可抓边缩放（新，BW=5）

旧版 `BORDER = 0`：**根本没法从边缘拉伸**（没有可命中的像素）。新版：

- frame 比 client 四周各大 **`BW = 5`** px（顶部额外多 `TB = 28`），这 5px 就是天然抓边；
- `_edge_at(cl, ex, ey)` 返回方向集合：左 / 右 / 下 及其组合（左上、左下、右上、右下）；
  **上边缘留给标题栏拖动**，不参与缩放（否则拖动窗口会误触发缩放）；
- `_button` 的 frame 分支：命中边 → 进入 `resize` 模式并记录初始几何 + 起始指针；
- `_motion` 的 `'resize'` 分支：按 edge 分量分别改 `x/y/w/h`，再 `_clamp` 到 `MIN_W/MIN_H`。

#### 15.6 几何节流：16ms 合并（新）

拖动/缩放时每个 MotionNotify 都 `configure` 会打爆 X server（QEMU 软渲染下直接卡死）。

- `_apply(cl)` 不再立即 configure，而是写入 `self._pending[cl]`；
- `_flush_pending(force)` 按帧合并下发，间隔 < `RESIZE_LIMIT_MS = 16` 的更新被丢弃（约 60fps 上限）；
- 只有**宽度变化**时才重画标题栏（缓存 `cl._last_fw`）——避免每行 Motion 都重跑一遍 cairo；
- 主循环改 `select` + `pending_events()` 非阻塞，事件一帧一批处理，不再阻塞在 `next_event()`。

对标：**Haiku 的后缓冲 + update session（脏矩形批处理）**、**SerenityOS 单显示服务 + 每窗口私有 backing store**、**Wayland attach+commit 原子提交**——三者共同思想是"**一批改动一次提交**"，我们这里是同一思想的最小实现。

#### 15.7 帧同步 `_NET_WM_SYNC_REQUEST`（EWMH，规范已定义，实现排 P1）

这是"拉伸怎么保证画面不撕裂"的**标准答案**，不是自己发明：

- client 在 `WM_PROTOCOLS` 声明 `_NET_WM_SYNC_REQUEST`，并把 XSync counter 写入 `_NET_WM_SYNC_REQUEST_COUNTER`；
- WM 要拉伸时发 ClientMessage(serial) → client 冻结重绘 → WM configure → client 画完把 serial 写回 counter → WM 解冻/合成器才提交这一帧。

python-xlib 自带 `ext.xsync`，可对接。当前原子已在 `SUPPORTED_ATOMS` 声明，实际收发排 **P1**（先把 picom 的 `use-damage` + `xrender-sync-fence` 打开即可拿到大部分收益）。

**picom 配置三件套（优化项）**：`use-damage`、`xrender-sync-fence`、`unredir-if-possible`；保留 `vsync`、`backend = xrender`、`corner-radius = 10`。

#### 15.10 本次新增的永久铁律

1. **frame 必须订阅 `ExposureMask`**，且几何/层级/焦点/标题每次变化后必须显式重绘（15.2）；
2. **`override_redirect` 窗口绝不能被 WM 托管**——桌面自绘层（ui_icons 的点击窗口、Dock、灵动岛、右键菜单）全部是 override_redirect。新增 `Client.overridden` + `is_managed()` 双重过滤，`_adopt_existing` 额外跳过 `override_redirect` 与名为 `qwm-frame` 的窗口。
   *事故*：qwm 重启后把 ui_icons 的 4 个 80×88 点击窗口 frame 成 890×593，层层套了 5 个 qwm-frame。
3. **reparent 语义铁律**：销毁 frame 会连带销毁其中的 client 窗口。qwm 退出前必须先把 client `reparent` 回 root 再 destroy frame → 新增 `cleanup()` + `SIGTERM/SIGINT` 处理器。
   *事故*：qwm 被 `kill -9` → frame 销毁连带 client 一起没 → picom 引用到已销毁窗口 → 进入"重定向了却不渲染"的坏状态（framebuffer 层确认窗口真的不可见，不是截图问题）。
4. **日志必须限频**：`log()` 同一消息 5 秒内只打一次并累计 `(+N 次重复)`。
   *事故*：`/tmp/qwm.log` 曾写至 **104MB / 209 万行**。
5. **`.xinitrc` 两处加固**：①picom 启动前先 `pkill -x picom`（避免坏状态残留）；②qwm 用 `/奇点OS/运行/qwm.py "$DISPLAY"` **跟随实际 display**，不要硬编码 `:0`。
   *事故*：重杀 Xorg 后 `/tmp/.X0-lock` 残留导致会话落在 `:1`，而 qwm 默认连 `:0` → qwm 根本没起来。
6. **`pkill -f` 自匹配陷阱（第三次出现）**：清理与启动必须拆成两条命令，且用 ASCII 模式（`pkill -9 -f "qwm\.py"`，**中文路径匹配会失败**）；杀 picom 用 `pkill -x picom`（`-f picom` 会连自己的 shell 一起杀）。

### G.16 点图标必须真的弹窗——单例 + 去 toast + 窗口不重叠 + qwm 自愈（2026-09-27 晚，用户令）

**用户令原文**："我点击一个图标，不用给我提示说打开了什么，直接弹窗就可以了。你说打开了，但是上面没有弹窗是怎么回事"

---

#### 16.1 现象与三个叠加根因

用户点桌面图标 → 系统弹 `启动 文件` 的 toast，但**看不到新窗口**。实机取证发现三重问题叠加：

| # | 根因 | 实证 |
| --- | --- | --- |
| **R1** | **应用没有单例**：`ui_icons._launch` 无脑 `subprocess.Popen(cmd)`，`ui_filebrowser / ui_album / ui_editor` 三个组件**根本没有 flock 单例** | 实测堆了 **6 个 `ui_filebrowser.py` 进程** |
| **R2** | **新窗口和旧窗口完全重叠**：`_smart_place` 找不到空位时一律**居中**，同尺寸应用一个压一个 | 实测 4 个 frame 全在 `(470,99)`，坐标一模一样 |
| **R3** | **qwm 有一段时间漏接 MapRequest**：窗口以 `(0,0)`、无标题栏的状态裸奔（root 直接子窗口），用户看着就像"没弹窗" | qwm 日志停在 `map …Ui_settings.py` 后再无记录，而 installer/filebrowser/album/xterm 全都起来了却没被纳管；窗口树里 `0x2c00003 884x620 @(0,0)` 等一批无 frame |

R1 + R2 合起来的观感就是：**第一次点能开，之后再点"开了但看不见"**——这正是用户描述的现象。

---

#### 16.2 修复

**① 统一单例 + 重复点击置前（`qd_ui_common.single_instance`）**

新增公共能力，替代各应用各自为政的 `_single_instance_or_exit`：

```python
# 先判锁再建窗口，避免第二个实例闪一下窗口
if not C.single_instance('filebrowser'):
    sys.exit(0)
win = FileBrowser()
C.set_raise_handler('filebrowser', win.present)
Gtk.main()
```

机制：`flock(LOCK_EX|LOCK_NB)` + 锁文件内写 PID。
- 抢到锁 = 主实例：登记 PID、挂 `SIGUSR1`；
- 抢不到 = 第二个实例：读 PID → `kill(pid, SIGUSR1)` → **让已有窗口 `present()` 置前** → 自己退出。

**编辑器特殊**：它是多文档应用，不能全局单例 → 锁 tag 按路径取 `md5(path)[:10]`，**同一个文件只开一个窗口，不同文件各开各的**（记事本行为）。

接入范围：`ui_filebrowser`（新增）、`ui_editor`（新增）、`ui_browser` / `ui_installer` / `ui_settings`（沿用既有锁，后续统一迁移）、`ui_album` 走既有 socket 单实例（不动）。

**② 去掉启动 toast（用户明确要求）**

`ui_icons._launch` 与 `ui_dock._activate` 中"启动成功"的 toast 全部删除。**窗口弹出来本身就是反馈**；只在**未安装 / 启动失败**时才提示（那才是用户需要知道的信息）。

**③ 窗口永不完全重叠（级联）**

`_smart_place` 找不到空位时，不再是"全部居中"，改为按已有窗口数级联偏移：

```python
n = len([c for c in self.clients.values() if c is not cl and c.is_managed()])
off = (n % 8) * CASCADE          # CASCADE = 32
cl.x = min(cx + off, max(0, self.sw - fw))
cl.y = min(cy + off, max(WORK_Y0, WORK_Y1 - fh))
```

**④ qwm 兜底自愈 `_sweep_orphans()`（每 3 秒）**

抽 `_adopt_one(child)` 供复用，主循环每 3 秒扫一次 root 子窗口，把**漏接的普通窗口补收编进 frame**（含重新 `_smart_place`，因为它大概率停在 `(0,0)`）。有了这层兜底，即使 MapRequest 偶发漏接，最多 3 秒内窗口也会拿到标题栏并被摆到正确位置。

**⑤ qwm 启动守卫**

`SubstructureRedirect` 全 server 只允许一个 client 持有。拿不到（BadAccess）时**直接 `SystemExit`**，绝不带着"能 frame 老窗口、却永远接管不了新窗口"的坏状态继续跑——那正是最难排查的一类故障表象。

#### 16.4 新增铁律

1. **任何"按需窗口"型应用必须单例**，且**重复点击要把已有窗口置前**——不是静默退出，否则用户点了没反应；
2. **启动成功的 toast 一律不弹**（用户令）。toast 只用于"用户需要知道但看不见"的信息：未安装、启动失败、错误；
3. **窗口摆放不得以"居中"兜底**——居中会让同尺寸应用完全重叠，必须级联错开；
4. **WM 必须能兜底收编漏接的窗口**：MapRequest 走事件，就一定要配一个周期性扫描兜底（R3 这类"静默失效"最难排查）；
5. **WM 拿不到 SubstructureRedirect 就退出**，不要苟活。

**遗留**：①一批早期残留的裸奔 xterm（`0x240000c` 等 `@(0,0)`）`map_state` 非 `IsViewable`，sweep 不收编也不销毁（无害，重启会话即清）；②`ui_browser` / `ui_installer` / `ui_settings` 仍用各自的旧锁，后续统一迁到 `C.single_instance` 以获得"置前"能力。

#### 17.2 怎么做的——工作流与验证方法论

**① 五步闭环（每轮都一样，不跳步）**

```
读（规范 + 记忆 + 源码，凭代码反推现状，不凭空假设）
 → 取证（上机跑命令拿证据：进程 / 窗口树 / 像素 / 日志，先定位根因再动手）
 → 改（本地改 → py_compile → 同步 Temp/g15 → SFTP 覆盖 /奇点OS/运行/）
 → 验（重启组件，必要时重建整个 X 会话 → 用 17.1 的手段实测）
 → 归档（写规范 + 双份同步 + 截图归档 ui_current_state/桌面截图/ + git 提交 + 写记忆）
```

**② 三条被本轮反复验证的方法论**

1. **先问"我们和谁同类"**——参照系选错，抄来的答案就是错的。G.15 一开始差点按 GNOME/KDE（合成式 WM）的思路找答案，而奇点OS 实际是 `Xorg + 堆叠 WM + 外挂合成器`，属于 **Openbox / i3 / bspwm / berry** 阵营。锁定 berry 之后，功能集才对得上量级。（详见 15.1）
2. **画面问题的第一嫌疑人永远是"有没有同步"，不是"画得够不够快"**——三键消失的根因不是"没画"，而是"画了但被 X server 抹掉且没人重绘"（缺 `ExposureMask`，见 15.2）。
3. **凡是"看不见的失效"，都必须配兜底**——事件驱动（MapRequest）再可靠也要配周期性扫描（`_sweep_orphans()` 每 3 秒，见 16.2④），否则就是最难排查的静默故障。

**③ 验证方法论（本轮沉淀，规范此前缺失）**

| 原则 | 做法 | 反例（本轮踩过） |
| --- | --- | --- |
| **不信截图，信像素** | `get_image` 取指定行，统计颜色种类与样例色值 | 曾因看不了图差点靠"日志没报错"判定标题栏没问题 |
| **不信"进程起了"，信窗口树** | 进程在 + 窗口是 root 直接子窗口且 `@(0,0)` = 用户眼里"没弹窗" | G.16 的 R3：6 个 filebrowser 进程在跑，用户一个窗口都看不到 |
| **用真实输入验证** | `xtest` 发真鼠标双击/拖拽，而不是命令行起进程 | 命令行启动成功 ≠ 用户点图标能开 |
| **每次改动以"体检"收尾** | 每组件实例数 / 僵尸数 / 日志字节数三项 | qwm 日志曾写至 104MB（104MB→114 字节靠限频 + 体检发现） |

**④ 会话重建手法（踩坑沉淀，操作层面）**

```
pkill -9 -f "qwm\.py"   # ASCII 模式；中文路径下 pkill -f 匹配会失败（第三次踩）
 → pkill -f "wait -n"   # 杀会话锚点
 → pkill -x Xorg        # 注意：杀 picom 要用 pkill -x picom，-f picom 会连自己的 shell 一起杀
 → getty 自动重建会话
```
- 陈旧 `/tmp/.X0-lock` 会让新会话落在 `:1` → qwm 必须跟随 `"$DISPLAY"`（15.10 铁律 5）；
- 重杀 Xorg 后必须**先清干净旧 qwm 再重建**，否则会出现"旧 qwm 连接已死但进程空转、仍被视为 WM 持有者"的双 qwm 并存态。

#### 18.4 VM 启动方式变更（重要运维知识）

`D:\iso\arch.img` 是**裸 ext4 根分区镜像**（无 MBR/无引导器，第一扇区全零）。**不能**用 `-drive ... -boot c` 磁盘引导（黑屏）。必须直连内核：

```
qemu-system-x86_64 -accel whpx -m 8192 -smp 4 \
  -kernel qemu/vmboot/vmlinuz-linux -initrd qemu/vmboot/initramfs-linux.img \
  -append "root=/dev/vda rw quiet" \
  -drive file=D:\iso\arch.img,format=raw,if=virtio,... \
  -net user,hostfwd=tcp::2222-:22 -vga std -display vnc=127.0.0.1:0
```

启动器：`qemu/启动开发VM.ps1`（vmboot/ 内核与 initramfs 用 debugfs 从镜像 /boot 提取）。内核参数**不要加 console=tty0**（fbcon 抢帧缓冲，Xorg FBIOPUTCMAP busy 的嫌疑人之一，已移除）。

### G.19 用户实测四问题修复 + picom 结论勘误 + opacity 标度事故（2026-09-28，用户报障）

**用户报障四条**：①设置里点"重启"组件消失且不再回来；②右键菜单可无限叠加；③灵动岛/快捷栏/菜单被黑色方框包裹；④连续右键弹出"剪切/复制/粘贴/插入表情符号"陌生窗口。

#### 19.1 问题③根因（本轮最重要发现，勘误 G.18）

**G.18 的"picom xrender+fbdev 不兼容"结论是错的。真根因：qwm 写 `_NET_WM_WINDOW_OPACITY` 标度错误。**

- EWMH 规定该属性是 **32 位标度**（`0xffffffff` = 不透明）；qwm 却直写 0-255 值（204/255）→ 合成器视为 **≈全透明** → 装帧窗口整体透明 → 露出黑壁纸 → "窗口存在但不可见"。
- 事故链：G.16 给 frame 加 opacity=204 起，**picom 开着时所有装帧窗口就全黑了**；G.18 误判 picom 不兼容将其禁用 → 又造成无 Alpha 合成 → OR 窗口（岛/Dock/菜单）圆角外变黑框（用户问题③）。
- 验证：手工把 frame opacity 改为 `0xffffffff`，xterm 立即恢复显示；xcompmgr 同样复现同样修复（排除 picom 个体问题）。
- **修复**：`_frame_create` 写属性前换算 `v32 = v8 * 0x01010101`；默认值恢复 204（80%，G.11 设计值）。picom 回归启动链（use-damage=false 保留——全量重绘，fbdev 下更稳）。
- **附**：XShape 方案在本环境实测无效（区域设置成功但 fbdev 渲染不裁剪，与早期记录一致），合成器是圆角/半透明的唯一可行路径。

#### 19.2 问题①设置"重启"失效（pkill 自杀 bug）

`_restart` 把"杀旧"与"拉新"写在**同一条 bash -c** 里：`pkill -f '[u]i_island.py'` 防了模式自匹配，但同一条命令行**后半段的组件路径**（`python3 .../ui_island.py`）仍被 pkill 匹配 → bash 杀死自己 → 重启永不执行。修复：杀/启拆两条命令，kill 用 `pgrep | xargs kill`。实测：点"灵动岛 重启"→ PID 4205→5289，岛消失 1 秒后回归。

#### 19.3 问题②右键菜单多开 + 问题④陌生窗口

- ②根因：菜单服务对每次 menu 请求都新建窗口，无单例。修复：模块级 `_current_menu`，`ContextMenu.__init__` 先销毁旧实例（**因果逻辑：全局唯一型界面必须单例**）。
- ④根因：多实例菜单的 seat grab 竞争——旧菜单销毁时的 ungrab 把新菜单的 grab 一并解除，后续点击穿透到底层窗口（编辑器 TextView）→ GTK 默认编辑菜单（剪切 T/复制 C/粘贴 P/删除 D/全选 A/插入表情符号 E）在点击位置弹出。单实例修复后竞争消失。
- 验收：10 连击仍只有 1 个菜单；服务不卡死；无陌生窗口。

#### 19.4 G.18 结论勘误表

| G.18 原结论 | G.19 勘误 |
| --- | --- |
| picom xrender+fbdev 下装帧窗口渲染为黑，picom 不兼容 | 根因是 opacity 标度错误；picom 修复后一切正常（装帧窗口/圆角/半透明全恢复） |
| use-damage=false 是修复 | 当时测量被叠加菜单污染，无效；真修复是标度换算。use-damage=false 仍保留（无副作用，全量重绘更稳） |
| 圆角暂失排 P1 | 已随 picom 回归恢复 |
| qd-install 属主 qduser 提权后门排 P0 | 仍有效待修（本轮未动） |

**教训（写入纪律）**：①EWMH 属性的标度必须逐字读规范，不能按直觉（0-255 直觉 ≠ 32 位规范）；②验收测量必须控制变量——本轮"use-damage 有效"的误判就是被画面里叠加菜单污染的像素测量骗了；③WM 与合成器的组合问题，先用最小属性修改（xprop 级）二分定位，再谈换组件。

#### 20.1 问题⑨——qwm v3：ARGB frame（本轮核心工程）

G.19 的 `_NET_WM_WINDOW_OPACITY` 方案把整窗（含 client 内容）一起变透明，被用户否决。正解：**frame 本身用 32 位 ARGB visual，按像素 alpha 绘制**——标题栏/边框半透明，client 内容完全不透明。

- **实现**：`_setup_argb()` 扫 depth-32 TrueColor visual（本机 0x40）；`_frame_create` 建 32 位 frame（`border_pixel=0` 必须显式给，否则 CreateWindow BadMatch——实测踩坑）；`_decorate_cairo` 标题栏+左右底边条分块 put_image（X 单请求 ≤262KB 约束）；alpha = settings.json opacity/255；`_NET_WM_WINDOW_OPACITY` 仅作 24 位回退路径。
- **两个关键坑（原型验证得出）**：①32 位窗口必须带 border_pixel；②put_image 必须在 map 之后（map 时 X 用背景色清屏，会把之前画的内容抹掉——测试脚本曾因此误判"ARGB 不渲染"）。
- **验收**：opacity=204 时标题栏像素 (33,34,36)=壁纸混合深灰、内容 (28,28,30) 不透明；opacity 204→121 标题栏实时 33→28。

```python
rgba = Gdk.Screen.get_default().get_rgba_visual()
if rgba: self.set_visual(rgba)
```

#### 21.2 最小化圆球机制（用户完整规格落地）

- **数据链**：qwm `_toggle_hidden` 记录 `cl.minimized_at` 时间戳 → 原子写 `/tmp/qd_minimized.json`（id/title/ts，按时间排序）→ 岛 500ms 轮询读文件 → 重建球。窗口销毁时同步刷新清单。

#### 25.2 AI 面板滚轮残影（ui_island.py）

#### 25.6 隐性 bug：设置「重启」按钮旧进程永远杀不掉（2026-09-29，用户报障：「设置 bug 依旧存在」）

**背景**：G.19 已修复设置里点「重启」组件消失不再回来——当时把 `pkill -f` 改成了 `pgrep -f '[u]i_%s\.py' | xargs -r kill`（防自杀模式），用户实测似乎通过。

**事实**：VM 上 `pkill`/`pgrep` 命令根本不存在（`/usr/bin/pkill` 未安装），`command -v pkill` 返回空 → 设置里点「重启」时旧进程永远杀不掉 → 新进程起不来或双进程竞争 → 用户看到的正是「点了重启没反应 / 组件消失后不再回来」。本机有 `pkill` 所以开发环境测不出来，**只有在真正的 VM/干净系统上才会复现**。

**修复**：`ui_settings.py` `_restart()` 和 `_restart_picom()` 增加 `command -v pgrep` 探测：
- 若 `pgrep` 存在 → 沿用 G.19 的 `pgrep -f '[u]i_%s\.py' | xargs -r kill` 防自杀模式；
- 若 `pgrep` 不存在 → fallback 到 `ps -eo pid,cmd | awk '/ui_%s\.py/ && !/awk/{print $1}' | xargs -r kill`；
- 两条独立命令不变：先杀旧再起新，起新时用 `export DISPLAY=:0` 而非 `DISPLAY=:0 …`（后者只有首条命令生效）。

**根因本质**：G.19 的表面修复只看「不自杀」，没看「命令在目标环境是否存在」。这是典型的「本机能跑、VM 跑不了」环境差异型隐性 bug——**只在干净的 Arch 底座上才暴露**。

#### 26.1 双击启动回归（ui_icons.py ClickAreas._serve）——最直接的「功能退化」证据（规范第 1159 行：双击图标才启动）

**根因**：G.25 拖拽改写时，把 G.14 的「双击」判定从 press 之间比较，错挪进了 ButtonRelease 分支，用「本次 press→release」间隔比较；而 `last` 又在 press 时刚更新为本次 press 时间戳 → 单击的 press→release 间隔必然 <0.4s → **单击即启动、双击启动两次**。表现为用户感觉「图标一碰就开 app、想开两个窗口却开了两个」。

**修复**（G.26 回归修复）：
- 双击判定移回 **press 之间比较**：`last["id"] == ev.window.id and now - last["t"] < 0.4` → 二次按下的 press 构成双击 → `bridge(_launch)` 启动一次并清空 `last`；
- 首次 press 只记录 `last` 与 `_drag` 候选（不启动）；release 只做拖拽 drop 与清理 `_drag`；
- 从此 **单击不启动、双击启动一次、拖拽（motion 超 8px 阈值）进 dragging 不误启动**，三态互不干扰，均经状态机模拟验证（单点/双击/隔 0.5s 两点/跨窗口双击/拖拽 6 场景全过）。

#### 26.2 配置覆盖竞争（qd_ui_common.py save_conf）——设置「改 A 丢 B」的真根因

**根因**：`save_conf(cfg)` 原实现是**整份 `json.dump(cfg)` 写盘**。各组件（ui_settings / ui_icons / ui_album）持有**启动时加载的旧快照 self.cfg**，任一组件保存会把其他组件新写入的键整份冲掉——例如拖拽落盘 `icon_pos` 后，设置页（旧快照里没有 icon_pos）任意改一项设置，`icon_pos` 就被整份覆盖消失 → 「拖拽位置莫名丢失 / 设置和拖拽互相打架」。

**修复**（G.26）：
- `save_conf(cfg, keys=None)` 支持**增量键保存**：keys 非空时先 `load_conf()` 读磁盘最新配置，仅把 keys 指定的键合并覆盖写回，其余键保留磁盘现值；keys=None 兼容旧整份调用；
- 写入改 tmp 文件 + `os.replace()` **原子替换**，多进程并发保存也不会写坏 JSON；
- 全部调用点改造（ui_settings.py 8 处 / ui_icons.py icon_pos / ui_album.py 1 处合并多键），离线模拟验证 4 场景（拖拽后设置页保存不冲 icon_pos、并发交替写键全保留、JSON 完整、兼容整份写）通过。

#### 26.3 qwm 标题栏透明度每次重绘都读盘（qwm.py _frame_opacity）——高频 IO + 不实时生效

**根因**：`_frame_opacity()` 每次 decorate 一个窗口就 `open(settings.json)` 读一次，拖窗/开关窗口多时反复 IO；且无任何命令触发强制重读 → settings.json 改透明度后 frame 不重绘 / 要等很久才生效。

**修复**（G.26）：
- `_frame_opacity` 改 classmethod + **2 秒缓存**（`_cached_opacity` / `_cached_opacity_ts` 类属性），缓存期内直接返回，不再读盘；
- `redecorate` 命令（设置页透明度滑块 → `qwmctl redecorate`）强制 `QWM._cached_opacity = None`，保证改后**立即**按新值重绘所有标题栏；
- 离线模拟验证：首次读、缓存命中、强制刷新、非法值回退 FRAME_OPACITY 且不污染缓存，4 场景全过。
